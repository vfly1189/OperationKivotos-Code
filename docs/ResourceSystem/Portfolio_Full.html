Addressables 위의 수명 스코프 리팩터

"안전한 쪽 = Global"로 도피하던 리소스 수명을, refCount 레지스트리 + 수명 스코프로 재구축해
상주 메모리를 회수하고 — 개발 빌드로 회수를 실측했다.

리소스의 실제 수명은 5종 이상인데 표현 수단이 2개(Global/Scene)뿐이라, 애매한 것이 전부 "안전한 쪽 = Global"로 도피해 영구 상주했다. 이를 (key,type) refCount 레지스트리 + 수명 스코프로 재구축해 상주 메모리를 회수하고, 수동 Release 코드는 한 줄도 추가하지 않았다. 이 문서는 문제 → 설계 → 여정 → 실측 → 방법론을 처음부터 정리한다.

1문제 — 2버킷의 구조적 결함

"버그"가 아니라 "표현력 부족" — 개발자를 Global 도피로 몰아넣는 구조였다.

초기 리소스 관리는 Global(영구) / Scene(씬) 두 버킷뿐이었다. 그런데 실제 수명은 훨씬 다양하다 — 팝업(스택 있는 동안)·파티(씬 넘어 생존)·던전(던전 동안)·영구. 표현할 계층이 없으니, "언제 해제해야 할지 애매한 것"은 전부 안전한 쪽(Global)으로 도피했고, 한 번 Global에 박힌 것은 게임 종료까지 안 내려왔다.

  • 중복·비대칭 — 같은 UI 기능인데 본체는 Global, 서브아이템은 Scene으로 수명이 갈라짐.
  • 수동 Release의 함정 — Addressables는 핸들 단위 수동 짝맞추기라, 호출부가 Release를 "기억"해야 하고 그 기억의 실패가 곧 누수였다.

3설계 — 2버킷 → 레지스트리 + 스코프

"누가 Release하나"라는 기억의 문제를, 수명 단위 자동 정산이라는 구조로 대체.

설계 3원칙

① 소유는 한 곳핸들 소유는 레지스트리 한 곳, 스코프는 티켓(HashSet<ResourceKey>)만 쥔다 → "누가 Release하나" 문제 소멸.
② refCount = 스코프 수스코프 내 중복 로드는 HashSet.Add 반환값으로 refCount 1. refCount = "이 핸들을 소유한 서로 다른 스코프 수".
③ 취소 ≠ 해제토큰은 기다림 중단만. 수명은 스코프 소유가 결정 → use-after-release가 구조적으로 불가.

수명 계층: Global(영구) · Scene(씬) · Party(파티 유지, 씬 전환 생존) · Popup(스택 있는 동안). — Dungeon 스코프는 측정상 이미 해결돼 만들지 않았다(§7 근거 기반 축소).

7방법론 — 결과물보다 "어떻게 판단했나"

이 리팩터의 진짜 값은 감축량이 아니라, 측정으로 판단하는 규율이다.

  • "측정 → 진단 → 구조 → 검증" 루프 — 각 단계가 자기 몫만 정리하고 나머지를 다음 단계에 정확히 넘김(잔여 증가가 3b/3d로 깔끔히 분해).
  • 숫자를 믿기 전에 도구를 검증 — 측정 도구가 아틀라스를 ×6.8 과대 계상하던 계통 오차를 플레이 모드 교차 검증으로 발견·보정. 계측 이관 후엔 isGlobal 한 줄만 토글해 단일 변수 A/B로 도구 등가성까지 실측(512.8MB 소수점 일치).
  • 계측이 기존 버그 3건을 드러냄 — 전부 뿌리가 "에셋 수명 ≠ 인스턴스 수명". "메모리가 줄었다"가 실은 누수를 못 센 결과일 수 있음을 R6에서 실증(합계 보존 = 유령이 회계에 드러남 = 성과 아닌 비용으로 정직 서술).
  • 근거 기반 축소 — Dungeon 스코프·프레임 예산 스트리밍·UI 루트 DDOL 대공사를 측정 근거로 제외. "명세를 따르지 않고 측정을 따랐다"(던전 왕복이 이미 +0.9MB).
  • 셀프 코드리뷰 — 취소 경로 유령 핸들 누수 + 아틀라스 중복 전개를 자가 발견·수정, 실측으로 누수 0·왕복 flat 재검증.

8면접 방어 질문 3종

질문답
"Addressables가 이미 refCount인데 왜 위에 또?"Addressables refCount는 핸들 단위 수동 짝맞추기 — 호출부가 Release를 '기억'해야 하고, 그 기억의 실패가 HP바 누수였다. 스코프는 기억을 구조(수명 단위 자동 정산)로 대체한 것.
"본인이 만든 문제를 본인이 고친 것 아닌가?"맞다, 숨기지 않는다. 2버킷은 초기 설계였고 계측으로 한계를 발견 → 개인의 주의력이 아니라 구조로 재발 차단. 이 프레이밍이 성장 서사.
"1인 프로젝트에 오버엔지니어링 아닌가?"팝업 세션 +287MB라는 측정치가 필요성을 증명. 반대로 던전 스코프·프레임 예산·DDOL 대공사는 측정 근거로 제외 = 필요한 것만 했다는 증거.

9한계 (반드시 동반)

  • 버킷별 절대값은 에디터 측정(CPU 사본 과대 계상) → 증감·비율만 인용. 단 총량 절대값은 개발 빌드 실측 확보(§6), Use Existing Build = 실제 번들로 증감·비율은 신뢰도 "강".
  • 그래픽스 드라이버 메모리는 지연 반납 특성 → 회수 판정 주 신호는 텍스처.
  • 히치 ms는 n=1~3, 15ms 이하 차이 주장 금지. TMP 동적 폰트가 세션마다 절대값을 흔드니 버킷 합계를 주 지표로.
