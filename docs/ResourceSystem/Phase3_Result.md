# Phase 3 결과 — 리소스 수명 재배치 (Lifetime Relocation)

> 기간: 2026-07-21 · 성격: **완료 보고 + 방어 논거**
> 상세 측정: [Baseline.md §9~§12](./Baseline.md) · 명세: [Phase3_Spec.md](./Phase3_Spec.md) · 버그 서사: [ProblemSolving_Log.md](./ProblemSolving_Log.md)

## 1. 한 줄 요약

2버킷 시절 "수명이 애매하면 안전하게 `isGlobal:true`" 관성으로 **거의 모든 리소스가 영구 상주**하던 것을, 각 리소스의 실제 수명 스코프로 재배치했다.
**진입 직후 Global 513 → 205MB(−60%), 세션 종료 합계 655 → 379MB(−42%), 영구 증가 +56 → +16MB(−72%).**

핵심은 수치가 아니라 **재발 차단 구조**다. 수동 `Release` 호출은 한 줄도 추가하지 않았다 — 스코프가 refCount를 자동 정산한다.

## 3. 수명 계층

```
enum ResourceScopeType { Global, Scene, Party, Popup }
```

| 스코프 | 수명 | Dispose 훅 | 담는 것 |
|---|---|---|---|
| **Global** | 부팅 → 종료 | **없음(불변)** | 공용 VFX 5, exitPopup, 상시 UI 3, DDOL 토스트 |
| **Scene** | 씬 진입 → 전환 | `ChangeSceneScope` (자동) | 맵·씬 UI·팝업 프리팹·아이콘 아틀라스 |
| **Party** | 파티 구성 → 교체 | `GameScene.CreateCharacters` (수동) | 인게임 캐릭 프리팹 |
| **Popup** | 스택 0→1 → 1→0 | `ClosePopupUI` (수동) | 스탠딩 이미지, ESC 데코 |

**Dungeon 스코프는 만들지 않았다.** 명세의 목표(던전 왕복 +18.7MB → 0)가 3a/3c로 이미 달성돼(측정 +0.9/−0.8MB), 근거 없이 스코프를 늘리지 않았다. → [Baseline §12-4](./Baseline.md)

### 순서 규칙 (Party·Popup 공통)

```
1. 인스턴스 파괴  (ClearParty / Destroy(popup))
2. 스코프 회전·Dispose
```

역순이면 **살아있는 인스턴스가 프리팹의 메시·텍스처를 참조하는 동안 핸들만 반납**되어 refCount는 풀려도 실제 언로드가 일어나지 않는다.

## 5. 비용 — 정직하게

lazy화는 공짜가 아니다. **상시 부담(진입 메모리)을 일회성 지연(첫 오픈)으로 바꾼 거래**다.

| 팝업 | 3a 이전 요청→표시 | 3c 이후 |
|---|---|---|
| UI_Info | 2.7 ms | **23.2 ms** |
| UI_Inventory | 1.4 ms | **15.2 ms** |
| UI_EquipmentUpgradePanel | 36.1 ms | 36.8 ms (원래 lazy, 대조군) |

- **재오픈은 전 팝업 8.9~10.6ms로 회귀 없음** (v2 기준 유지)
- `[LoadStats]` 재로드 키 18 → 21개 — 아틀라스가 씬마다 재로드된다
- 스탠딩 재로드 실측: 첫 로드 197ms, **재로드 ~4ms**(실제 번들 환경 값)

즉 **진입 −308MB의 대가 = 팝업 첫 오픈 +14~20ms.** 이 트레이드오프를 측정으로 판단한 것이 이 단계의 핵심 활동이다.

### R6은 성과가 아니라 비용이었다

`UI_LootNotification`을 Global로 되돌리자 Global +140.8 / Scene −141.0 / **합계 −0.3** — 완벽한 보존. 이전에는 "핸들은 반납됐는데 인스턴스는 살아있는" 유령이라 **어느 버킷에도 안 잡혔다.** 세션 종료 합계가 259 → 391MB로 늘어난 것도 버그 수정의 정직한 비용이며, 성과로 포장하지 않는다.

> **"메모리가 줄었다"는 지표가 실은 누수를 세지 못한 결과일 수 있다.** Before/After를 볼 때 합계 보존 여부를 먼저 확인해야 하는 이유.

## 6. 계측이 도구였다 — 드러난 버그 3건

셋 다 **Phase 3가 만든 것이 아니라, 스코프화와 다버킷 계측이 드러낸 기존 버그**다. 공통 뿌리는 **"에셋의 수명 ≠ 그 에셋으로 만든 인스턴스의 수명"**.

| # | 버그 | 정체 |
|---|---|---|
| **5-4 / R6** | `UI_LootNotification` use-after-release | DDOL 인스턴스 + static 캐시 + Scene 스코프 에셋. 던전 왕복 후 재로드도 안 됨 |
| **3a 동반** | `_isLoadingPopup` 미복구 | 조기 반환 시 플래그가 true로 남아 **이후 모든 팝업 영구 차단** |
| **R6 동반** | `PreloadAsync` 영구 정지 | 로드 실패 시 `_instance`는 null인데 플래그만 내려가 `WaitUntil`이 무한 대기 |

**교훈**: 스코프를 고를 때 "누가 이 에셋을 쓰는가"가 아니라 **"그것으로 만든 것이 언제까지 사는가"**를 물어야 한다.

### 계측 자체의 버그도 2건

| # | 문제 | 조치 |
|---|---|---|
| 로드 통계 소실 | `RecordLoad` 호출부가 R1 죽은 코드 제거 때 함께 삭제됨 → 이후 모든 측정에서 `[LoadStats] 기록 없음` | `ResourceRegistry` 캐시 미스 경로에 재배치 |
| assert 위치 오류 | "이전 씬 미반납"을 잡겠다면서 실제로는 "회전 후 새 적재"를 잡음 (매 전환 오탐) | 검사를 await 이전으로 이동 + 취소된 획득 되돌리기 |

**교훈**: 죽은 코드를 지울 때 **그 안에 살아있는 계측이 얹혀 있는지** 확인해야 한다. 계측은 기능이 아니라 눈에 안 띄므로 함께 사라져도 즉시 티가 안 나고, 몇 단계 뒤 "왜 이 지표가 비지?"로 돌아온다.

## 7. 방법론 — 측정 설계

**단일 변수 A/B.** Baseline v2는 옛 2버킷 딕셔너리로 잰 값인데 그 사이 R2가 계측을 레지스트리 기반으로 갈아엎었다. 도구가 바뀐 구간을 두고 직접 차감하면 성과와 도구가 섞인다. → **`isGlobal` 한 줄만 토글해 같은 도구로 Before를 재측정**했고, 그 쌍만 비교했다.

부수 소득: 재측정한 Before의 ①=512.8 / ②=515.4MB가 **v2의 512.8 / 515.5와 소수점까지 일치** → 도구 등가성이 실측으로 확인돼 기준선 연속성을 확보했다.

> **숫자를 믿기 전에 그 숫자를 만든 도구를 먼저 검증했다.**

측정 중 한 번은 조건 통제에 실패했다(3a After 로그와 Before 로그의 변수가 둘 다 달라 짝이 안 맞음). 재측정으로 바로잡았고, 그 과정을 §9-1에 남겼다.

| **약** | 히치 ms | n=1~3. §8-5 기준 **15ms 이하 차이는 주장 금지** |

- **미해결**: `UI_Info` 첫 오픈 히치가 3c 세션에서 563.6ms까지 튀었다가 3b 이후 103~120ms로 안정. 정상 범위는 v2(123.4ms) 수준이나 **563ms의 원인은 미규명**(이상치로 추정, 확정 불가).
- **미측정**: 개발 빌드 실측. 계측의 절반(`[ResourceMemory]` 버킷 MB)이 `EditorUtility.CollectDependencies` 의존이라 **런타임 오버레이를 새로 만들어야** 가능하다.
- 시나리오가 세션마다 완전히 동일하지 않았다(팝업 오픈 순서·구성). 다음 측정부터 고정 필요.
