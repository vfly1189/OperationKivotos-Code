## 2. 몬스터 코드 현재 상태 (2026-09-28 점검)

> **2026-09-29: Phase 1 완료.** 아래는 착수 전 스냅샷이다. 결과·최종 계약은 [Phase1_Result.md](Phase1_Result.md).

### 2.1 미커밋 리팩터 — 절반 진행

생명주기 계약([MonsterSimulation/Audit/Lifecycle.md](../MonsterSimulation/Audit/Lifecycle.md))을 코드에 옮기던 중이다.

**들어간 것**
- `BaseMonsterController`에 `OnSpawn(SpawnContext)` / `OnDespawn()` 정의
- `OnEnable`에서 CTS 생성·상태 리셋 제거 → `OnSpawn`으로 이동
- `Node.Reset()` 추상 메서드 + 전 노드 구현 (M5 대응)
- 파티 구독을 `Start` → `OnSpawn`, 해제를 `OnDespawn` (L0 대응)
- `Start` 본문 주석 처리, Ranged에 `ResetAmmo()`를 `OnSpawn`으로

**빠진 것 — 핵심**
- **`OnSpawn` / `OnDespawn`을 부르는 곳이 0개** (L2 그대로). `IPooledMonster.cs`는 `using UnityEngine;` 한 줄, `SpawnContext`는 private 필드 3개뿐

### 2.2 그래서 지금 워킹트리는 동작하지 않을 가능성이 높다

`_monsterCts`가 이제 `OnSpawn`에서만 만들어지는데 `OnSpawn`이 호출되지 않는다.

| # | 증상 (추정) | 위치 |
|---|---|---|
| W1 | 원거리 몹 활성화 시 NRE — `_monsterCts.Token` (프리웜 `Create()` 경로 포함) | `RangedMonsterController.OnEnable` |
| W2 | 사망 처리에서 NRE — **죽은 몹이 풀로 회수되지 않음** | `BaseMonsterController.HandleDeadState` → `DespawnAsync(_monsterCts.Token)` |
| W3 | 공격 시 NRE — `TryCast(..., _monsterCts.Token)` | AR / RL / Tank 컨트롤러 |
| W4 | 타겟을 못 얻어 **전부 Idle** — 파티 구독이 `OnSpawn`에만 있음 | `NormalMonsterController` |
| W5 | **HP바 중복 생성** — `OnEnable`마다 무조건 생성, 반납은 사망 경로에만. Sector 이탈로 회수된 산 몹을 다시 꺼내면 HP바가 하나 더 생김 | `NormalMonsterController.OnEnable` |
| W6 | `WaitNode.Reset()`이 `_duration`까지 0으로 → 재사용 시 대기 0초. **구조(생성자 설정)와 상태를 섞음** (보스 전용이라 현재 무증상) | `BTNode.cs` |

→ 이 상태로는 영상을 찍을 수 없다. 다만 **경계 소실은 Sector 정책(`DespawnMonsters`가 산 몹을 즉시 회수)에서 나오고
Phase 1~4는 그 정책을 건드리지 않는다.** 그래서 Before 영상은 생명주기를 고친 뒤 **Phase 4 하네스 경로로** 찍는다.
마감은 **Phase 5 착수 전** (현상을 없애는 건 Phase 5). 같은 경로라 After 영상과 나란히 비교할 수 있다.

목표 흐름 (계약 그대로):

```
스폰   Pool.Pop()          비활성 인스턴스
       position/rotation   agent 안 건드림
       Stat.SetStat()      데이터 주입
       OnSpawn(ctx)        CTS · 상태 · 타겟 · 구독 · BT 리셋 · HP바 요청   ← 비활성

회수   Resource.Destroy → Pool.Push
```

## 5. 리스크

| 리스크 | 대응 |
|---|---|
| 결과가 밋밋함 (FPS 차이 작음) | 헤드라인을 문제 지표(경계 소실 · 스파이크 · 화면 밖 비율)로. 예측을 먼저 박제해 두면 "예측대로"도 결과가 됨 |
| B는 스폰/디스폰이 잦아 스폰 비용에 불리 | 스폰 1회 비용을 따로 기록 — "거리 방식의 본질"과 "내 스폰 구현"을 분리 |
| 하네스 전투 재현성 | 경로 · 속도 고정, 3회 편차를 먼저 확인 (4-5) |
| Phase 1이 길어짐 | 완료 조건을 수치로 고정해 둠. 조건 충족 시 즉시 다음으로 |
| 리쉬 복귀가 NavMesh·BT와 얽혀 커짐 | 최소 구현(집 좌표로 이동 + 도착 판정)만. 연출은 나중 |
