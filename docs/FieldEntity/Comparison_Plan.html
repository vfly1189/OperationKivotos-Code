Field Entity · 03 비교 계획서

존재 판정 비교 계획서

단일 Sector의 문제에서 출발해 7개 방식을 비용과 현상으로 비교하고 하나를 채택한다. 이 문서가 비교 트랙의 작업 순서 기준이며, 02_Plan의 Phase 4~8을 대체한다(번호는 Phase 0부터 다시 셈).

1. 문제 상황

단일 Sector 방식 — 서 있는 섹터만 켜고, 벗어나면 끈다

경계선에서 갑자기 사라지거나 나타난다현상

사라짐 — 몬스터를 끌고 경계를 넘으면 쫓아오던 몬스터가 눈앞에서 사라진다. "언제 회수하나?"에 대해 위치·전투 여부를 안 보고 섹터가 꺼지는 즉시 회수해서 생긴 문제.

나타남 — 새 섹터에 들어서는 순간 경계 근처 몬스터가 한꺼번에 생긴다. 섹터 단위로 켜기 때문에 생긴 문제(판정 단위).

비용이 과다하게 쓰인다비용

유지 비용 — 섹터가 크면 화면에 안 보이는 영역까지 연산한다(켜진 몬스터의 약 90%가 화면 밖).
순간 비용 — 섹터가 바뀌는 순간 그 섹터 몬스터 전부를 한 프레임에 생성·회수한다(최대 119마리).

섹터를 사람이 직접 지정한다작업

신규 맵이나 크기 조정 시 에디터에서 구역·스포너 소속을 일일이 다시 맞춰야 한다. 경계 문제를 인접 섹터로 풀면 인접 표까지 관리해야 한다.

2. 원인 진단

사라짐 = 회수 규칙의 문제판정 방식과 무관하다. 모든 방식에 공통 몬스터 규칙을 둔다: 교전 중이면 유지, 교전이 끝나면(리쉬 귀환 포함) 회수.
나머지 = 섹터 크기 하나에 묶임나타남 · 유지 비용 · 순간 비용 · 사람 작업. 작게 하면 비용은 줄지만 경계와 인접 표가 늘고, 크게 하면 반대. 크기 조정으로는 못 푼다.

7. 단계

이미 끝난 바탕: 몬스터 생명주기(입구 팩토리 · 출구 Resource.Destroy) · 스포너 재설계(슬롯 상태 기계 · ReadyAt · Gen) · Sector 판정 버그 수정 · 리쉬

Phase 0 — 사전 작업

  • 0-1 결정 고정 — 거리 켜기 20m(화면 9.1 + 스포너 퍼짐 5.5 + 여유) / 끄기 25m 확정(RL 감지 15m + 퍼짐 5.5m보다 0.5m 짧아 경로 0.15%에서 화면 밖 1마리 부재 — 감수) · ③ 3×3·20m, ④ 5×5·10m(보장 반경 20m) · ⑥ 5×5·13m(조건 (K−1)/2·S ≥ 끄기 반경) · ⑦ 반경 0 구 · 밴드 {20, 25} · band 1 = 유지 · 청크 원점 (−90, −45)(원점 분포 중간, Chunk_Origin.pdf) · 리쉬 25m 유지 · 메인 측정은 스폰 예산 무제한 · 탈락 조건. 바꾸면 이전 측정 무효.
  • 0-2 공통 몬스터 규칙 — 교전 유지 (아래 그림). IsEngaged 공개 = 사망 아님 ∧ (추적 · 공격 · 장전 · 귀환 중). 누수 검증 = 유예 목록 크기 로그가 귀환 시간 안에 0. Before용 스위치(교전 유지 + 리쉬 함께 끔).
  • 주의: 귀환 이벤트만 구독하면 "집 2m 안에서 교전하다 대상 놓침"은 귀환이 안 일어나 영원히 남는다 → 이벤트가 아니라 매 틱 상태 확인으로 한다.
  • 0-3 정책 이음새 — IActivationPolicy: 플레이어 위치 → 원하는 활성 스포너 집합. SpawnerManager가 차이만 켜고 끔. 정책은 씬 로드 전에 선택(런타임 전환 금지 — 전체 회수 스파이크 + 지터 난수 순서 변화). 켜고 끈 로그 저장. 기존 SectorManager 판정을 ① 정책으로 이동.
  • 0-4 계측 — 5절 항목 전부. ProfilerMarker(정책 선택 · 스포너 틱 · 스폰 단계별 · 회수), 생성·회수 시점 뷰포트 판정, [PoolGrow] + 풀 최대 사용량, 개발 빌드 로그 → CSV.
  • 0-5 하네스 — 웨이포인트 + 고정 속도 자동 주행, 파티 무적. 구간 ⓐ 팔 순회 ⓑ 끌고 가기(주행 속도 ≤ 몬스터 속도 — 빠르면 "대상 놓침" 귀환으로 소실이 안 생김) ⓒ 섹터·칸 경계 1m 왕복 10회. 씬 로드 직후 구간 버림 · 개발 빌드 · 같은 시드. ①로 3회 편차 확인.
  • 0-6 예측 박제 — 6절을 커밋. 0-7 Before 영상 — 단일 Sector · 공통 규칙 끔 · ⓑ 구간.

Phase 1 — 몬스터 1마리 비용 환산

  • 활성 0 / 50 / 100 / 200마리 고정(교전 없음 / 교전 중) → 프레임 시간 기울기 = 1마리당 μs
  • 시간 분해: 행동 트리 · NavMesh · 애니메이터 · HP바 / 스폰 1회 분해: 풀 꺼내기 · SetStat · OnSpawn · SetActive / 회수 1회
  • 메모리: 풀 0 → 200 생성 전후 차이
  • 산출: 환산표 + "1마리 시간이 어디서 나가는가" 막대그림. 이게 있어야 "활성 186 vs 33"을 ms로 말할 수 있다.

Phase 2 — 정책 구현

  • ② 인접 표는 박스 겹침으로 자동 계산 → 사람이 검수. 검수 작업을 목록으로 기록(사람 작업 비교 자료)
  • ③④ 스포너를 로드 때 1회 칸에 등록, 플레이어 칸이 바뀔 때만 후보 갱신(완료, SpotlightActivation) · ⑤ 스포너 중심 거리 · ⑥ 창 + 원 · ⑦ CullingGroup — 콜백은 쌓아 두고 다음 선택에서 반영, 씬 Clear에서 Dispose
  • 동등성 검증: ⑤와 ⑥의 켜고 끈 로그가 프레임 단위로 같은지, ⑤와 ⑦은 1프레임 어긋남만 빼고 같은지. 다르면 Phase 3 진행 안 함
  • 방식별 "새 맵 하나 적용 시 사람이 할 일" 목록

Phase 3 — 메인 측정

  • ①~⑦ × 3회, 같은 경로 · 같은 빌드 · 정책만 바꿈 → 비용 표 + 현상 표 + 활성 수 타임라인 · 프레임 시간 분포
  • 선택 변형: 밀도 ×1.5 · ×2(약 550 · 700마리) / 공통 프레임 스폰 예산

Phase 4 — 선택 비용 경계

  • 게임 밖 C# 벤치마크: 합성 스포너 23 / 100 / 1,000 / 10,000(같은 밀도로 맵을 넓힘) · ⑤ 단순 루프 vs ⑥ 격자(후보 캐시) · 교차점
  • ⑦ CullingGroup은 카메라가 렌더링해야 갱신 → 빈 씬 + 카메라 + 합성 스포너로 따로. 메인 스레드 시간과 엔진 컬링 시간을 나눠 기록
  • "이 장르 규모에선 ⑥ · ⑦ 불필요"가 나와도 그대로 채택 — 청크 격자 · CullingGroup을 안 쓴 근거가 된다.

Phase 5 — 판정 · 채택 구현

  • 탈락 조건 → 우열 확인 → (엇갈리면) 점수 + 가중치 민감도
  • 채택 방식을 실제 맵 기본 정책으로. 교체 조건(스포너 수)을 코드 주석 · 문서에 기록 · Sector 볼륨의 운명(삭제 / 게임플레이 구역)
  • 예측(6절) 대조 — 틀린 곳은 틀렸다고, 왜 틀렸는지 · After 영상(Before와 같은 ⓑ 구간)

Phase 6 — 결과 문서 · 포트폴리오

  • 04_Result.md + PDF — 서사 순서 그대로: 문제 → 진단 → 예측 → 측정 → 결론 → 한계(싱글 · 맵 1개 · 측정 환경)
  • 슬라이드: 문제 + Before / 진단(묶인 손잡이) / 6개 방식 그림 / 비용 표 · 현상 표 / 결론 + After + 한계
