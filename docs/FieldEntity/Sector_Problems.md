## 0. 결론 — 최종 문제 정의

**전제: 리쉬(추적 상한 → 넘으면 위치·체력 원복)는 어떤 방식이든 항상 적용한다.**

| # | Sector 방식의 문제 | 근거 |
|---|---|---|
| 1 | 경계에서 팝인/팝아웃 → 인접 섹터가 필요 → **인접 표 작성·검수** | S2→S1 진입 시 경계 6m 안 S1 자리 20개가 눈앞에서 등장 |
| 2 | 새 맵마다 **섹터 분할 + 스포너를 섹터 소속으로 배치 + 인접 표** | 소속 = 섹터의 자식(`GetComponentsInChildren`) |
| 3 | 안 보이는 곳도 섹터 모양·크기만큼 활성화 (**유지 비용**) | 켜진 몹의 87%가 화면 밖 (인접 켜두기 시 94%) |
| 4 | 섹터가 켜지고 꺼질 때 그 크기만큼 한꺼번에 처리 (**순간 비용**) | S4 진입 = 119마리 한 프레임 요청 / 인접 시 S3→S2에서 102 켜기 + 119 회수 동시 |
| 5 | **리쉬 거리가 섹터 폭보다 길 수 없음** (길면 따라온 몹이 사라짐) | 인접 켜두기 기준 스폰 → 꺼지는 곳 최소 27~31m |

> **1·3·4·5가 전부 섹터 크기 하나에 묶여 있다.**
> 작게 나누면 3·4는 좋아지지만 1·5가 나빠지고, 크게 하면 반대가 된다.
> 그래서 크기 튜닝으로는 안 되고, **판정 방식 자체를 바꿔야 한다** → 거리 방식(B) 비교의 근거.

## 2. 측정 전 검증 (2026-10-02)

"지금 구조로 측정해도 되나"를 확인했다. 정책과 실행 사이의 경계(정책은 스포너 id만 켜고 끔)는 측정 가능한 상태였고, 아래 4개가 숫자를 오염시킬 수 있었다.

| # | 항목 | 판단 | 처리 |
|---|---|---|---|
| ① | 계측 없음 — 경계 소실 · 화면 밖 비율 · 프레임당 스폰 등이 코드에 없음 | 측정 준비 문제 | Phase 4에서 구현 |
| ② | 풀 30 vs S4 119 → 첫 진입 프레임에 즉석 생성 89회가 섞임 | 정책 비용이 아님 | **첫 바퀴 기록은 버림** (200마리 수준도 성능상 문제 없음 — 유저 확인) |
| ③ | 재현성 — 수동 조작 · 피격 전멸 텔레포트 · 몹 몸통 차단 | 측정 방법 문제 | Phase 4 하네스 + 무적(`SetPartyInvincible`) |
| ④ | **Sector 구현 버그** — 트리거 이탈을 무시 + 1.4~2.3m 겹침 → 겹침에 발을 들였다 물러나면 서 있는 섹터는 꺼지고 다른 섹터가 켜진 채로 굳음 | **Sector 버그** — 고치지 않으면 "망가진 Sector를 이겼다"는 반박을 받음 | **수정 · 플레이 확인 · 커밋 `1872a610`** |

④ 수정 내용: "켜진 섹터는 하나"를 버리고 **"현재 캐릭터가 안에 서 있는 섹터는 켜고, 아닌 섹터는 끈다"**로 바꿨다(겹침에서는 둘 다 켜짐).
판정은 트리거 이벤트 대신 `SectorManager.OnUpdate`가 매 프레임 현재 캐릭터 위치로 한다. 로딩 중 빈 파티 · 캐릭터 교체 · 텔레포트에서 이벤트 순서에 기대지 않기 위해서다.
덤으로 거리 방식(B)과 같은 입력(매 프레임 플레이어 위치)을 쓰게 됐다.

> 겹침을 없애는 것만으로는 안 됐다. 플레이어 트리거 캡슐(지름 약 0.4m)이 경계를 밟으면 양쪽에 걸쳐 같은 버그가 났다.
> `OnTriggerExit`의 주석만 풀면 더 나빠졌다. 매니저가 "지금 켜진 섹터"를 잘못 기억한 채 아무 섹터도 켜지지 않았다.

비차단(알고만 있을 것): 프레임 예산 `int.MaxValue`(Sector의 실제 동작이라 기준선에서는 유지) · Gen 불일치 경로 미검증(켜고 끄기가 잦은 B에서 중요).
`_lastDestPosition` 미리셋은 리쉬 구현(9절) 때 같이 고쳤다.

> ②는 이후 유저가 `GameScene.CreatePool`의 풀 크기를 30 → 200으로 올려 첫 진입 즉석 생성 자체가 없어졌다(미커밋).

## 3. 첫 질문 — 경계 소실은 인접 섹터로 해결되나 (리쉬 없음)

### 3.1 현상
플레이어가 몹을 달고 소속 섹터를 완전히 벗어나는 순간, 그 섹터 출신 산 몹이 전부 즉시 회수된다.
`SpawnerManager.DeActivate`의 Alive 분기 → 구독 해제 → `Resource.Destroy` → 슬롯 Waiting · `ReadyAt = now`.

### 3.2 원인
**몬스터는 움직이는데 소속은 태어난 섹터에 고정돼 있다.** 몬스터의 운명은
`플레이어 위치 → Sector 판정 → 스포너 끄기 → 슬롯 회수`로 정해지고, **몬스터의 현재 위치·전투 여부는 한 번도 보지 않는다.**
화면 밖이어도 문제다. 쏘던 몹이 갑자기 없어지고, 돌아가면 만피 새 몹이 서 있다("도망치면 초기화").

### 3.3 인접 섹터를 켜두면
- **좋아지는 것:** 가만히 있는 몹의 팝인/팝아웃이 화면 밖으로 밀린다. S3→S2 통로에서 새로 켜지는 S1은 최소 29.5m, 꺼지는 S4는 최소 42.5m 떨어져 있다. 화면은 9m까지다.
- **못 고치는 것: 따라온 몹 소실.** 꺼지는 시점이 한 칸 늦어질 뿐이다. S4 몹을 끌고 S3를 지나 S2에 들어서면 S4가 꺼지고, 몹은 여전히 플레이어 옆에서 사라진다.
- **대가:** 켜진 몹 최대 119 → 193 (섹터별 170 · 176 · 193 · 193 · 187), 화면 밖 87% → 94%, 넘을 때 큰 섹터 둘이 동시에 바뀜, 인접 표 관리. 바둑판 맵이면 주변 8칸까지 9칸이 켜진다.

→ 경계 소실의 원인은 판정 단위가 아니라 **회수 규칙**이다. 해결은 정책과 무관한 **몬스터 규칙(리쉬)**이다.

### 3.4 정정 (지난 대화)
"어디서 싸워도 이웃 경계까지 15m 이내라 경계 소실이 자주 난다"고 했는데 **틀렸다.** 이웃과 맞닿는 곳은 통로뿐이고, 감지 거리 안에서 이웃으로 넘어갈 자리는 363개 중 81개다(1절).
→ 경계 소실은 "팔에서 몹을 달고 통로까지 끌고 왔을 때" 난다. **Before 측정 경로는 일부러 그렇게 짜야 한다.**

## 4. 전제를 바꿈 — 리쉬를 항상 적용하면

일반적인 게임처럼 "어느 정도 거리까지는 따라오고, 상한을 넘으면 위치·체력이 원위치"를 모든 방식에 적용한다고 가정한다.

따라온 몹이 사라지지 않으려면, 섹터가 꺼지기 전에 몹이 먼저 포기하고 돌아가야 한다.
즉 **리쉬 거리 < 스폰 자리에서 그 섹터가 꺼지는 곳까지의 거리**여야 한다.

| 방식 | 스폰 자리 → 꺼지는 곳 최소 거리 (섹터별) | 가능한 리쉬 |
|---|---|---|
| 서 있는 섹터만 | S1 **0.8** · S2 9.7 · S3 21.0 · S4 10.4 · S5 6.9m | 1m 미만 → 사실상 불가능 |
| 인접 섹터 켜두기 | S1 28.4 · S2 27.3 · S3 28.5 · S4 30.7 · S5 29.9m (두 칸 떨어진 섹터까지 직선거리) | 약 25m 이하 |

- **리쉬 + 인접 섹터**면 따라온 몹 소실은 거의 없어진다.
- "도망치면 초기화"는 버그가 아니라 **의도된 규칙**이 된다(리쉬 자체가 원복).
- 대신 **리쉬 최대치가 섹터 폭(이 맵 30m)에 묶인다** → 0절 5번.

## 5. 그래도 남는 Sector의 문제 — 0절 표의 근거

1. **팝인/팝아웃 → 인접 표.** 박스 겹침으로 자동 계산은 된다. 하지만 자동 계산은 "닿아 있다"만 알고 "걸어갈 수 있다 · 보인다"는 모른다.
   벽 너머 섹터나 멀리 내다보이는 섹터는 사람이 검수해야 하고, 맵을 고칠 때마다 다시 맞춰야 한다. 빠진 칸은 조용한 버그가 된다.
2. **저작.** 스포너 설치는 어떤 방식이든 필요하다. Sector만의 비용은 박스 분할 · 섹터 소속(자식 배치) · 인접 표다.
   계층을 옮기면 소속이 조용히 바뀌고, 박스가 겹치면 이중 활성(S4+S5 = 187), 틈이 있으면 아무 섹터도 안 켜진다.
3. **유지 비용.** 통로를 지나가기만 해도 팔 끝 90m까지 켜진다. 화면에 동시에 보이는 몹은 평균 약 12마리인데, 켜지는 건 최대 119마리다. 화면 밖 몹도 행동 트리와 NavMesh는 계속 돈다.
4. **순간 비용.** 켜지는 순간 슬롯 전부가 같은 프레임에 요청한다. S3는 6마리, S4는 119마리로 **20배** 차이다. 스파이크 크기를 필요가 아니라 박스 크기가 정한다.
5. **리쉬 제약.** 4절 표.

## 6. 근본 — 섹터 크기라는 손잡이 하나

섹터 크기를 돌리면 세 가지가 같이 변하는데, 원하는 방향이 반대다.

```
               섹터를 작게  ←──────────→  섹터를 크게
비용 (3·4)      ✅ 줄어듦                   ❌ 늘어남
리쉬 (5)        ❌ 짧아짐 (금방 포기)         ✅ 길게 가능
팝인 (1)        ❌ 눈앞에서 생길 위험          ✅ 화면 밖에서 생김
```

수도꼭지 하나로 온도와 수압을 같이 조절하는 샤워기와 같다. 하나를 맞추면 다른 게 틀어진다.

**거리 방식(B)은 손잡이가 따로 있다.**

| 손잡이 | 무엇에 맞춰 정하나 |
|---|---|
| 활성 반경 | 화면 크기 → 팝인 방지 |
| 리쉬 거리 | 게임플레이 — "몇 m까지 쫓아올지" |
| 비용 | 스포너 단위로 켜지므로 박스 크기와 무관 |

## 7. 비교 분석으로 가는 이유와 틀

**이유:** Sector의 문제는 크기 튜닝으로 풀리지 않는 결합(6절)이고, 거리 방식은 그 결합을 끊는다. → "Sector를 개선하는 방식"으로 거리 · 청크 등을 비교한다.

### 7.1 거리와 청크는 대등한 후보가 아니다

| | 무엇인가 | Sector 문제를 푸나 |
|---|---|---|
| **거리 (B)** | 플레이어 ↔ 스포너 거리로 켜고 끔 | 푼다. 손잡이가 분리됨 |
| **청크 단위 활성** | 맵을 자동 격자로 나누고 주변 N칸을 켬 | 일부만. 저작은 자동이 되지만 **칸 크기가 비용·리쉬를 정하는 결합은 그대로** |
| **청크 + 거리 (C)** | 격자는 "가까운 스포너 찾기"용, 판정은 거리 | 결과는 B와 같고, 스포너가 많을 때 **판정 비용만** 줄임 → 질문이 다름 (B vs C 확장) |

선택지: 청크 단위 활성을 중간 단계로 끼우면 `손으로 그린 구역 → 자동 격자 → 거리` 세 지점이 된다.
문제를 "손으로 그려서"(저작)와 "구역이라서"(결합)로 갈라 보여줄 수 있다. 구현이 하나 늘어나므로 **미정**.

### 7.2 리쉬는 모든 방식에 똑같이
- **Before:** 지금 Sector, 리쉬 없음 — 경계 소실 영상
- **비교:** 모든 방식에 리쉬를 켜고 정책만 바꿈. 리쉬 유무로 결과가 갈리면 정책이 아니라 리쉬를 잰 것이 된다

### 7.3 문제마다 지표 하나

| Sector 문제 | 지표 |
|---|---|
| 1 팝인/팝아웃 | 화면 안에서 생성·회수된 횟수 |
| 3 유지 비용 | 화면 밖 비율 · 최대 활성 수 |
| 4 순간 비용 | 한 프레임 최대 스폰·회수 수 |
| 5 리쉬 제약 | 리쉬를 늘렸을 때 경계 소실이 생기기 시작하는 거리 |
| 2 저작 | 새 맵 적용 시 사람이 할 작업 목록 |

평균 FPS는 헤드라인이 아니라 참고 지표다(363마리 규모에선 차이가 작음 — 계획서와 같음).

### 7.4 Sector가 맞는 경우
판정 비용이 거의 0이고, 구역이 지역명·BGM·필드 보스 같은 게임플레이 단위와 겹친다.
문으로 닫힌 던전 방처럼 **경계가 실제 벽과 일치하는 곳**에서는 Sector가 맞다.
이 맵(통로 + 팔, 열린 경계)이라서 거리가 맞다고 말한다.

## 9. 리쉬 구현 (2026-10-03, 미커밋 · 플레이 미확인)

| 항목 | 내용 |
|---|---|
| 위치 | `NormalMonsterController` (AR · RL · Tank 공통). 보스는 별도 컨트롤러라 제외 |
| 집 | `OnSpawn`에서 `SpawnContext.Position`을 NavMesh 위로 맞춰 저장 |
| 발동 | ① 집에서 수평 거리 `_leashRange`(기본 25m)를 넘으면 ② 집에서 2m 넘게 떨어져 있는데 대상이 감지 거리 밖이면(쫓아왔다가 놓침). 행동 트리 `사망 → **리쉬** → 전투 → 추적 → 대기` |
| 귀환 중 | 리쉬 노드가 Running이라 **감지·추적·공격 노드는 평가조차 안 됨** · 무적 · 공격 애니 이벤트 무시 · 정지거리 0 (추적용 `사거리 − 0.5`로는 집 앞 수 m에서 멈춤) |
| 도착 | 체력 원복(`Health.Recover`, HP바 갱신) · 탄약 원복(원거리) · 정지거리 복구 · 대상을 현재 캐릭터로 다시 맞춤 · 대기 |
| 막힘 | `_returnTimeout`(8초) 넘으면 집으로 `Warp` |
| 적용 범위 | **필드 스포너가 만든 몹만** (`SpawnerManager`가 `EnableLeash()`). 던전 웨이브 · 보스 소환 몹은 리쉬 없음 |
| 스위치 | `NormalMonsterController.LeashEnabled` — `BenchmarkTester` **F3**로 켜고 끔 (Before 녹화 = 끔) |
| 로그 | `[Leash] … 귀환 시작 (너무 멀어짐 / 대상 놓침) — 집에서 N m` · 시간 초과 시 경고 |

복귀 여부는 `_state`와 **따로** 플래그(`_isReturning`)로 둔다. 원거리 몹의 공격·장전 종료 애니 이벤트가 `_state`를 Idle로 덮어쓰기 때문이다.
같이 고친 것: `_lastDestPosition`을 `OnSpawn`에서 리셋(재사용 몹이 이전 생애의 목적지를 기억하던 문제).
