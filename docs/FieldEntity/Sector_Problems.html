Sector 방식의 문제 정의

측정 전에 "Sector가 정확히 무엇이 문제인가"를 정리한 기록이다. 측정 전 검증 → 인접 섹터 검토 → 리쉬 전제 → 최종 정의 → 비교 이유 순서로 고민했다. 수치는 실제 맵(BackStreetMap.prefab)과 카메라(Game.unity) 값으로 계산한 기하값이며, 플레이 측정값이 아니다.

결론 — 리쉬(추적 상한 → 넘으면 위치·체력 원복)를 항상 적용한다는 전제에서
#Sector 방식의 문제근거 (계산값)
1경계에서 팝인/팝아웃 → 인접 섹터 필요 → 인접 표 작성·검수S2→S1 진입 시 경계 6m 안 자리 20개가 눈앞에서 등장
2새 맵마다 섹터 분할 + 스포너 소속 배치 + 인접 표소속 = 섹터의 자식 (GetComponentsInChildren)
3안 보이는 곳도 섹터 모양·크기만큼 활성화 — 유지 비용켜진 몹의 87%가 화면 밖 (인접 시 94%)
4섹터가 켜지고 꺼질 때 크기만큼 한꺼번에 — 순간 비용S4 진입 = 119마리를 한 프레임에 요청
5리쉬 거리가 섹터 폭보다 길 수 없음인접 기준 스폰 → 꺼지는 곳 최소 27~31m
1·3·4·5가 전부 섹터 크기 하나에 묶여 있다. 작게 나누면 3·4가 좋아지지만 1·5가 나빠지고, 크게 하면 반대가 된다. 크기 튜닝으로는 안 되고 판정 방식 자체를 바꿔야 한다 → 거리 방식 비교의 근거.
그림 1 · 실제 맵 — 위에서 본 모습 (축척 그대로)
좌표: 맵 프리팹의 섹터 BoxCollider와 스폰 포인트 363개. 화면 범위: _delta (0, 5, -3) · 시야각 60° · 16:9 (건물 가림 무시). 북쪽(위)이 카메라가 바라보는 방향. 계획서의 "화면 ≈ 25m" 가정은 틀렸다.

정책 → 스포너 id 켜기/끄기 경계는 측정 가능한 상태. 아래 4개가 숫자를 오염시킬 수 있었다 (2026-10-02)
#항목성격처리

③재현성 — 수동 조작 · 피격 전멸 텔레포트 · 몹 몸통 차단측정 방법Phase 4 하네스 + 무적

④ 버그가 생기던 순서수정 전

① S4에서 겹침 구간에 발을 들임 → "S3 진입" → S4 끄고 S3 켬
② 다시 S4 쪽으로 물러남 → S3 이탈은 무시, S4는 나간 적이 없으니 진입 신호도 없음
→ S4에 서 있는데 몹 0마리. 고치지 않고 비교하면 "망가진 Sector를 이겼다"는 반박을 받는다.

④ 수정 — 서 있는 섹터는 켜고 아니면 끔1872a610

"켜진 섹터는 하나"를 버림. 겹침에서는 둘 다 켜진다. 판정은 트리거 대신 SectorManager.OnUpdate가 매 프레임 현재 캐릭터 위치로 한다. 로딩 중 빈 파티 · 캐릭터 교체 · 텔레포트에서 이벤트 순서에 기대지 않으려고. 덤으로 거리 방식과 입력이 같아졌다.

기각한 대안 — 겹침 없애기: 플레이어 캡슐(지름 약 0.4m)이 경계에 걸쳐 같은 버그가 남는다. OnTriggerExit 주석만 풀기: 매니저가 "켜진 섹터"를 잘못 기억한 채 아무것도 안 켜진다. 비차단: 프레임 예산 int.MaxValue(Sector의 실제 동작) · Gen 불일치 경로 미검증(B에서 중요). ②는 이후 풀 크기 30 → 200으로 해소(유저 수정).

1. 첫 질문 — 경계 소실은 인접 섹터로 해결되나 (리쉬 없음)

몹을 달고 소속 섹터를 완전히 벗어나는 순간, 그 섹터 출신 산 몹이 전부 즉시 회수된다
그림 2 · S4에서 쫓아온 몹을 달고 S3로 넘어갈 때 (현재 규칙: 서 있는 섹터만 켬)
코드: SpawnerManager.DeActivate의 Alive 분기 — 구독 해제 → Resource.Destroy → 슬롯 Waiting · ReadyAt = now. 몹이 지금 어디 있는지, 싸우는 중인지는 보지 않는다.
그림 3 · 몬스터의 운명이 정해지는 길 — 몬스터 자신은 한 번도 물어보지 않는다
원인 몬스터는 움직이는데 소속은 태어난 섹터에 고정돼 있다. 섹터가 꺼질 때 "그 섹터 출신 산 몹 = 즉시 회수"이므로 몹을 끌고 벗어나는 순간 전투가 통째로 사라진다. 화면 밖이어도 문제다. 쏘던 몹이 갑자기 없어지고, 돌아가면 만피 새 몹이 서 있다("도망치면 초기화").
그림 4 · 인접 켜두기에서 S4 몹을 끌고 S2까지 갈 때 — 사라지는 곳이 한 칸 밀릴 뿐
인접 섹터로 좋아지는 것팝인·팝아웃

가만히 있는 몹이 켜지고 꺼지는 모습이 화면 밖으로 밀린다. S3→S2 통로에서 새로 켜지는 S1은 최소 29.5m, 꺼지는 S4는 최소 42.5m 떨어져 있다. 화면은 9m까지다.

못 고치는 것 · 대가그림 4

따라온 몹 소실은 그대로다(한 칸 지연). 대가: 켜진 몹 119 → 193, 화면 밖 87% → 94%, 넘을 때 큰 섹터 둘이 동시에 바뀜(102 켜기 + 119 회수), 인접 표 관리. 바둑판 맵이면 9칸.

정정 — 지난 대화 "어디서 싸워도 이웃 경계까지 15m 이내라 경계 소실이 자주 난다"는 틀렸다. 이웃과 맞닿는 곳은 통로뿐이고, 감지 거리 안에서 넘어갈 자리는 363개 중 81개다. → 경계 소실은 "팔에서 몹을 달고 통로까지 끌고 왔을 때" 난다. Before 측정 경로는 일부러 그렇게 짜야 한다.

2. 전제를 바꿈 — 리쉬를 항상 적용하면

"어느 정도까지 따라오고, 상한을 넘으면 위치·체력이 원위치" — 일반적인 게임의 규칙을 모든 방식에 적용

따라온 몹이 사라지지 않으려면 섹터가 꺼지기 전에 몹이 먼저 포기해야 한다. 즉 리쉬 거리 < 스폰 자리에서 그 섹터가 꺼지는 곳까지의 거리.

그림 5 · 스폰 자리 → 소속 섹터가 꺼지는 곳까지 최소 거리 = 리쉬의 상한
"서 있는 섹터만" = 이웃 섹터 박스까지의 최소 거리. "인접" = 두 칸 떨어진 섹터 박스까지의 직선거리(실제 걷는 길은 더 길다).
정리 리쉬 + 인접 섹터면 따라온 몹 소실은 거의 없어지고, "도망치면 초기화"는 버그가 아니라 의도된 규칙이 된다(리쉬 자체가 원복). 대신 리쉬 최대치가 섹터 폭(이 맵 30m)에 묶인다. 이것이 결론 표의 5번이다.

3. 그래도 남는 Sector의 문제 — 결론 표의 근거

리쉬로 몬스터 쪽 문제를 걷어낸 뒤에도 Sector라서 생기는 문제
그림 6 · 플레이어가 S3 통로에 있을 때 켜지는 범위
S3 자체는 6마리뿐인데 이웃 S4(119)와 S2(68)의 팔 끝까지 켜진다. 그 몹들은 통로에서 34~100m 떨어져 있다.
1. 팝인/팝아웃 → 인접 표저작 · 검수

박스 겹침으로 자동 계산은 된다. 하지만 자동 계산은 "닿아 있다"만 알고 "걸어갈 수 있다 · 보인다"는 모른다. 벽 너머나 멀리 내다보이는 섹터는 사람이 검수해야 하고, 맵을 고칠 때마다 다시 맞춰야 한다. 빠진 칸은 조용한 버그가 된다.

2. 새 맵마다 저작저작

스포너 설치는 어떤 방식이든 필요하다. Sector만의 비용은 박스 분할 · 섹터 소속(자식 배치) · 인접 표다. 계층을 옮기면 소속이 조용히 바뀌고, 겹치면 이중 활성(S4+S5 = 187), 틈이 있으면 아무 섹터도 안 켜진다.

3. 유지 비용 — 안 보이는 곳까지화면 밖 87%

통로를 지나가기만 해도 팔 끝 90m까지 켜진다. 화면에 동시에 보이는 몹은 평균 약 12마리인데 켜지는 건 최대 119마리다. 화면 밖 몹도 행동 트리와 NavMesh는 계속 돈다.

4. 순간 비용 — 크기만큼 한꺼번에스파이크

켜지는 순간 슬롯 전부가 같은 프레임에 요청한다(_spawnBudgetPerFrame = int.MaxValue). S3는 6마리, S4는 119마리로 20배. 스파이크 크기를 필요가 아니라 박스 크기가 정한다.

5. 리쉬 거리가 섹터 폭보다 길 수 없음그림 5

인접 섹터를 켜도 리쉬는 약 25m가 한계다. "몇 m까지 쫓아오게 할지"라는 전투 감각을 기획이 아니라 맵을 어떻게 나눴느냐가 정한다.

4. 근본 — 섹터 크기라는 손잡이 하나

하나를 돌리면 세 가지가 같이 변하는데, 원하는 방향이 서로 반대다
그림 7 · Sector는 손잡이 하나, 거리 방식은 손잡이 셋

5. 비교 분석으로 가는 이유와 틀

Sector의 문제는 크기 튜닝으로 풀리지 않는 결합이고, 거리 방식은 그 결합을 끊는다 → "Sector를 개선하는 방식"으로 거리 · 청크를 비교한다

5.1 거리와 청크는 대등한 후보가 아니다

방식무엇인가Sector 문제를 푸나
거리 (B)플레이어 ↔ 스포너 거리로 켜고 끔푼다 — 손잡이가 분리됨 (그림 7)
청크 단위 활성맵을 자동 격자로 나누고 주변 N칸을 켬일부만. 저작은 자동이 되지만 칸 크기가 비용·리쉬를 정하는 결합은 그대로
청크 + 거리 (C)격자는 "가까운 스포너 찾기"용, 판정은 거리결과는 B와 같고 스포너가 많을 때 판정 비용만 줄임 → 질문이 다름 (B vs C 확장)

선택지(미정): 청크 단위 활성을 중간 단계로 끼우면 손으로 그린 구역 → 자동 격자 → 거리 세 지점이 된다. 문제를 "손으로 그려서"(저작)와 "구역이라서"(결합)로 갈라 보여줄 수 있다. 구현이 하나 늘어난다.

5.4 Sector가 맞는 경우

판정 비용이 거의 0이고, 구역이 지역명·BGM·필드 보스 같은 게임플레이 단위와 겹친다. 문으로 닫힌 던전 방처럼 경계가 실제 벽과 일치하는 곳에서는 Sector가 맞다. "무조건 거리가 좋다"가 아니라 이 맵(통로 + 팔, 열린 경계)이라서 거리가 맞다고 말한다.
