Operation Kivotos · 필드 엔티티 관리 · 00 방식 지도

넓은 필드에서 누구를 살려두고, 얼마나 자주 돌릴 것인가

현재 Sector 방식을 출발점으로, 필드 엔티티(몬스터·NPC)를 관리하는 방식들을 그림으로 나란히 놓는다. 결론을 먼저 정하지 않고, 각 방식이 무엇을 풀고 무엇을 남기는지를 본다.

0. 질문부터 쪼갠다 — 세 장면은 서로 다른 문제다

"필드 몬스터 관리"라고 한 단어로 부르지만, 장면마다 비용을 만드는 변수가 다르다.

① 이 트랙이 다루는 세 장면

①은 "어디를 켤까", ②는 "켜진 것을 얼마나 싸게 돌릴까", ③은 "무엇을 메모리에 둘까"가 문제다. 한 방식으로 셋을 다 풀 수 없다.

② 층으로 보면 — 층마다 '반경'이 다르다 이 문서의 좌표계

위로 갈수록 비싸고 반경이 좁다. 이 문서의 A~D는 결국 "②존재 층의 반경을 무엇으로 정하느냐"의 차이이고, ①·③·④는 그와 별개로 겹쳐 쓰는 층이다. (거리 수치는 개념도)

NPC도 같은 틀에 들어간다 NPC는 대개 움직이지 않고 전투도 안 하므로 ②존재 층만 관리하면 되고 ①틱 비용은 거의 0이다. 이 문서는 몬스터로 설명하지만, "정적인 것은 공간으로 판정한다"는 규칙은 NPC·채집물·상호작용 오브젝트에 그대로 적용된다.

1. 출발점 — 현재 Sector 방식과 경계 문제

트리거 볼륨(Sector)에 들어가면 그 구역 스포너를 전부 켜고, 이전 구역은 통째로 끈다. SectorManager.OnPlayerEnterSector

③ 플레이어가 A→B로 넘어간 직후 (현재 규모: Sector 5 · 스포너 23 · 몬스터 363)

1번이 눈에 보이는 버그지만, 2·3번이 구조의 한계다. 1번만 고치면 2·3·4번은 그대로 남는다.

④ 떠오르는 두 가지 패치 — 둘 다 '증상'만 막는다

원인은 하나 판정 단위가 사람이 그린 구역이라는 것. 구역이 화면보다 크고, 경계가 임의의 위치에 있고, 손으로 유지해야 한다. 그래서 다음 방식들은 모두 판정이 기하학(격자·거리)에서 자동으로 나오게 만드는 방향이다.

2. 방식 A — 맵 전체를 균일한 청크(격자)로 나눈다

좌표를 셀 크기 S로 나누면 셀 번호가 나온다. 구역을 그릴 필요가 없다. 플레이어 셀 + 주변 셀만 켠다.

⑤ 플레이어 주변 3×3 활성, 5×5까지는 유지 (히스테리시스)

경계 문제는 "주변 셀도 켠다(3×3)"로 사라지고, 경계선 왕복 깜빡임은 "켜는 범위 < 끄는 범위"(3×3 / 5×5)로 막는다.

풀어주는 것
  • 저작 비용 0 — 구역을 그리지 않는다
  • 셀 조회 O(1). 맵이 커져도 판정 비용이 그대로
  • 셀은 에셋 로드 단위·저장 단위로도 쓸 수 있다 (리소스 시스템과 연결점)
  • 같은 격자를 몬스터 이웃 탐색·광역기 판정에 재사용 가능
남기는 것
  • 셀 크기 S를 골라야 한다 — 너무 작으면 churn, 크면 낭비
  • 활성 영역이 네모 → 방향마다 켜지는 거리가 다르다
  • 셀 경계를 넘을 때 3~5개 셀이 한꺼번에 바뀐다 (작은 스파이크)
  • 밀도가 고르지 않은 맵에선 셀마다 비용 편차가 크다

3. 방식 B — 플레이어와의 거리로만 판단한다

스포너마다 플레이어와의 거리를 재서 가까우면 켜고 멀면 끈다. 구역도 격자도 없다.

⑥ 거리 밴드와 히스테리시스

반경이 하나면 경계선 위에서 왔다 갔다 할 때 매 프레임 켜졌다 꺼진다. 켜는 선과 끄는 선을 떨어뜨리면 그 사이에선 이전 상태가 유지된다.

풀어주는 것
  • 경계가 존재하지 않는다 — 고친 게 아니라 없앤 것
  • 고정 각도 쿼터뷰에선 "플레이어 중심 반경 = 화면"이라 화면에 딱 맞게 켤 수 있다
  • 저작 비용 0, 격자 크기 고민도 없다
  • 한 번에 켜지는 건 반경에 막 들어온 몇 개뿐 → 진입 스파이크가 자연히 분산
남기는 것
  • 전수 검사 — 매번 모든 스포너와 거리를 잰다 (N이 커지면 비례)
  • 팝인 — 반경에 들어오는 순간 없던 게 생긴다 (반경을 화면보다 넉넉히)
  • 자유 카메라 3D에선 "거리 = 시야"가 깨진다 (멀리 보이는 산 위 몬스터)
  • 밀집엔 무력 — 다 가까이 있으면 거를 게 없다
등록 대상은 몬스터가 아니라 스포너 스포너는 움직이지 않으니 위치를 한 번만 등록하면 된다. 몬스터를 등록하면 매 프레임 위치를 다시 써야 하고, 개수도 10~20배다. 몬스터 무리를 "스포너 하나"로 대표시키는 것 자체가 이 장르에 맞는 선택이다. (움직이는 몬스터 문제는 5절 ⑧)

4. 방식 C — 청크로 후보를 좁히고, 거리로 판정한다 (A + B)

충돌 판정의 Broad phase / Narrow phase와 같은 구조. 청크 = "누구를 검사할지", 거리 = "켤지 말지".

⑦ 두 단계 판정

1단계 Broad — 청크반경의 외접 사각형이 걸치는 셀만 꺼낸다 (보라 영역). 이 셀들에 등록된 스포너 k개만 후보.
2단계 Narrow — 거리후보 k개만 실제 거리 + 히스테리시스로 판정. 판정 비용이 전체 N이 아니라 k에 비례.
덤 — 반경을 층마다 따로청크는 로드(에셋)에, 거리는 존재(오브젝트)에 쓴다. 0절 ②의 층 구조가 이 조합에서 자연스럽게 나온다.
솔직한 단서지금 맵은 스포너 23개라 전수 거리 검사도 사실상 공짜다. 이 조합의 값어치는 CPU보다 맵이 커져도 구조가 안 바뀐다는 것과 격자를 로드·AI·판정에 재사용한다는 데 있다.

널리 알려진 예: 마인크래프트는 청크를 로드하는 거리(렌더 거리)와 개체를 실제로 돌리는 거리(시뮬레이션 거리)를 따로 둔다. 언리얼 World Partition은 월드를 격자 셀로 나누고, 플레이어 같은 '스트리밍 소스' 주변 반경의 셀만 로드한다.

5. 어느 방식을 골라도 남는 문제 — 움직이는 엔티티

스포너는 가만히 있지만 몬스터는 플레이어를 쫓아 움직인다. Sector·청크·거리 전부 똑같이 부딪힌다.

⑧ 스포너는 범위 밖, 몬스터는 플레이어 바로 옆

정적인 것(스포너·NPC) = 공간으로 판정청크/거리/무엇이든.
움직이는 것(몬스터) = 자기 상태로 판정 전투 중이면 스포너가 꺼져도 살아 있다 → 전투가 끝나면 리쉬로 집 복귀 → 도착 후 스포너 상태를 따른다. 유예 상한(N초)을 둬서 영원히 안 꺼지는 경우를 막는다.
결론이건 방식 선택이 아니라 소유권 규칙으로 푼다. 1절 패치②(전투 중 유지)와 리쉬가 여기서 다시 쓰인다.

6. 그 밖의 방식들

D는 A의 변형, E·F·G·H는 다른 층을 다루는 방식이다 — A·B·C와 경쟁하지 않고 겹쳐 쓴다.

D계층 공간 분할 (쿼드트리)

존재 층 · A의 변형

빽빽한 곳만 더 잘게 쪼갠다. 격자의 "셀 크기 하나로는 못 맞춘다" 문제에 대한 답.

  • 밀도가 극단적으로 불균일한 맵에 강함
  • 움직이는 개체는 매번 트리 재배치 비용
  • 고도차 없는 평면 맵이라 옥트리까지는 불필요
언제: 한쪽에 몬스터 수백, 나머지는 텅 빈 맵. 우리 맵(무리 단위·고른 배치)엔 균일 격자로 충분할 가능성이 높다.

E중요도 · LOD 틱 등급

틱(품질) 층 · 끄지 않고 느리게

아무도 사라지지 않는다. 먼 것은 생각(BT 평가)만 드물게, 이동·회전 보간은 매 프레임.

  • 밀집에서 효과가 있는 유일한 방식 — 다 가까이 있어도 등급을 나눈다
  • 팝인이 원천적으로 없다
  • 메모리는 1바이트도 안 준다 / 총량 N에 여전히 비례
  • 전제: 몬스터마다 도는 Update()를 매니저 하나로 모아야 함
언제: A·B·C 위에 겹쳐서. 카오스 던전형(밀도 문제)에서는 주력.

F엔티티 가상화 — 레코드와 오브젝트 분리

레코드 층 · 화면 밖 세계를 멈추지 않는 법

"몬스터가 존재한다"와 "몬스터 오브젝트가 있다"를 분리한다. 오브젝트는 레코드의 보이는 얼굴일 뿐.

  • 꺼졌다 켜져도 리스폰 타이머·처치 상태가 이어진다
  • 오브젝트를 풀까지 반납해도 세계는 유지 → 메모리를 실제로 줄일 수 있는 전제
  • 지금은 이 레코드를 스포너가 BaseMonsterController[]로 쥐고 있어 오브젝트와 한 몸이다
언제: A·B·C 어떤 걸 쓰든 같이 필요. 반오픈월드의 "한 번 잡은 적은 그대로" 같은 영속 상태의 기반.

G지역 스트리밍

로드 층 · 오픈월드 / 반오픈월드

존재 판정보다 한 단계 바깥 — 에셋·지형을 메모리에 올릴지를 정한다.

  • 반오픈월드: 맵을 몇 개로 끊고 전환 시 로딩(텔레포트·문). 맵 하나 안에서는 다시 A~C
  • 오픈월드: 격자 셀을 반경 기준으로 끊김 없이 로드 — C를 로드 층에 쓴 것
  • 이 프로젝트의 Addressable 리소스 스코프가 바로 이 층의 부품
언제: 맵 하나를 통째로 올리면 메모리가 모자랄 때. 현재 BackStreetMap 규모엔 불필요.

H인카운터 · 웨이브 예산

존재 층 · 카오스 던전형 (공간이 아니라 시간으로)

아레나가 좁아 전부 화면 안 → A~C는 거를 게 없다. 대신 수와 속도를 제어한다.

  • 동시 생존 상한 + 프레임당 스폰 수 제한(스파이크 분산)
  • 풀 선(先)워밍 — 웨이브 최대치만큼 미리
  • 개체당 비용 줄이기: 개별 경로탐색 대신 공유 경로(플로우 필드), 매니저 일괄 업데이트, 인스턴싱/ECS
언제: 밀도가 문제일 때. E와 한 세트. 이 프로젝트에 이 장면을 넣을지는 별도 결정.

—참고: 서버의 관심 영역 (AOI)

이 프로젝트는 완전 싱글 — 범위 밖, 정리만 해 둔다

MMO의 필드 몬스터는 서버가 시뮬레이션하고, 서버가 "이 클라에게 무엇을 보낼지"를 격자·거리로 정한다(Interest Management). 그 경우 존재 층은 서버로 올라가고, 클라에는 받은 것을 얼마나 싸게 보여줄지(틱·연출 품질)만 남는다.

  • 그래서 A~C를 클라에서 직접 만들어 보는 것 = 서버 AOI를 로컬에서 재현해 보는 것과 같은 공부
  • 반대로 E(품질 층)는 서버가 있어도 클라 몫으로 남는다

7. 한 장 비교

"좋다/나쁘다"가 아니라 "무엇을 풀고 무엇을 남기나". 층이 다른 방식끼리는 우열 비교가 아니라 조합 대상이다.

방식층저작 비용경계 문제판정 비용맵이 커지면밀집메모리
현재 Sector존재높음 (수동)있음트리거 이벤트 (≈0)구역도 커짐무력안 줆 (풀 유지)
A 청크존재·로드0 (자동)이웃 셀 + 유지 범위로 해소O(1) 셀 계산비용 고정무력셀 = 로드 단위 가능
B 거리존재0없음 (히스테리시스)O(N) 전수 — CullingGroup으로 저렴N에 비례무력켤 것만
C 청크+거리존재·로드0없음O(k) 후보만비용 고정무력로드/존재 반경 분리
D 쿼드트리존재0없음O(log N) · 재배치 비용좋음밀도 편차엔 강함—
E 중요도/LOD틱0해당 없음 (끄지 않음)버킷 관리N에 비례유일하게 효과안 줆
F 가상화레코드레코드 설계——필수에 가까움—줄일 수 있는 전제
G 지역 스트리밍로드중간 (레벨 분할)로딩 경계—이게 답—실제로 줆
H 웨이브 예산존재웨이브 데이터없음 (아레나)—해당 없음상한·예산으로 제어선워밍 필요
표를 읽는 법 A·B·C·D는 같은 칸(존재 층)을 두고 경쟁한다 — 여기서 하나를 고른다. E·F·G·H는 다른 칸이다 — 고른 것 위에 필요한 만큼 얹는다. "청크 vs 거리 vs 둘 다"라는 원래 질문의 답은 C에 가깝고, 진짜 질문은 "그 위에 무엇을 얹을까"다.

8. 장면별 조합

0절의 세 장면에 층별로 무엇을 끼우는가.

⑨ 장면 × 층

진한 칸 = 그 장면의 주 전장. 장면마다 주 전장이 다른 층에 있다 — 0절에서 "세 문제는 다른 문제"라고 한 이유다.

9. 이 프로젝트에 대한 제안

출발점(Sector) → 다음 한 걸음. 결정은 아직 아니고, 다음 대화에서 정할 것들을 모아 둔다.

제안 — 존재 층을 C(청크 + 거리)로 ① Sector의 네 문제(경계·단위·노가다·스파이크)를 한 번에 없앤다 — 패치가 아니라 판정 기준 교체.
② 청크 격자가 로드 층(리소스 시스템)과 판정 쿼리(어빌리티 광역기)에 재사용될 자리를 만든다 — 세 대주제를 잇는 고리.
③ 맵을 키우거나 두 번째 필드를 붙여도 구조가 그대로다.
단, 우리 규모(스포너 23개)에선 B(거리만)로도 충분히 돌아간다. B로 먼저 만들고, 청크는 "후보 추리기"로 나중에 끼우는 순서도 가능하다.

다음에 정해야 할 것

  1. 범위 — 세 장면 중 무엇을 이 프로젝트에서 실제로 만들까? (연속 필드는 확정. 좁은 아레나 대량(H+E)을 추가할지 / 오픈월드(G)는 설명만 할지)
  2. 반경 — 화면 ≈ 25m 기준으로 진입·이탈 반경 (후보: 35m / 50m). 셀 크기 S (후보: 화면 한 변 정도 = 25m 전후)
  3. 등록 단위 — 스포너로 확정해도 되는지 (NPC·채집물도 같은 등록기에 넣을지)
  4. 움직이는 몬스터 규칙 — 전투 중 유예, 리쉬 복귀, 유예 상한 N초
  5. 레코드 분리(F) — 스포너가 쥔 BaseMonsterController[]를 포인트별 상태 레코드로 바꿀지, 리스폰 타이머를 절대 시각으로 옮길지
  6. Sector의 운명 — 삭제 / 게임플레이 구역(지역 이름·BGM·필드 보스) 용도로 역할 변경
  7. 측정 — 무엇으로 "나아졌다"를 말할지. 기존 MonsterSimulation 트랙의 계측(활성 수·히칭·팝인)을 그대로 가져올지
선행 조건 (기존 점검에서 이미 나온 것) 몬스터 생명주기 계약(OnSpawn/OnDespawn 미배선)과 풀 프리워밍 부족(풀 30 vs 섹터 최대 119)은 어떤 방식을 고르든 먼저 성해야 한다. 방식을 바꾸면 스폰/디스폰 횟수가 늘어나는 쪽이라, 이 둘이 깨져 있으면 방식의 차이가 아니라 풀·생명주기 결함을 재게 된다. (근거: docs/MonsterSimulation/Audit/Lifecycle.md, Comparison/07_Prerequisites.md — 현재 미커밋 작업에서 진행 중일 수 있음)
