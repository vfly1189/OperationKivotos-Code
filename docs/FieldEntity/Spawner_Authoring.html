Operation Kivotos · 필드 엔티티 관리 · 스포너 저작 방식

스포너는 세 질문의 답이다 — 어디에, 어떤 자리에, 무엇을

지금 스포너는 폐기하고 새로 만든다. 비교 주제는 Sector 방식 vs 거리 방식(+청크). 두 방식 모두 스포너를 쓰므로, 스포너를 어떻게 배치·정의하느냐를 먼저 정한다. 이 문서는 제안된 두 방법의 장단점과 실제로 쓰이는 다른 방식 네 가지를 비교한다.

결정 (2026-09-29) — 방법 1 채택, 나머지는 기록으로 보존 비교 결과는 저작 방식과 무관하고(정책은 위치·반경만 봄), 669개 포인트는 이미 배치돼 있어 1번의 단점(노가다)이 추가로 들지 않는다. ③ 베이크는 에디터 도구 2~3일이 드는데 비교 결과에 영향이 없다. → 데이터 형식(손 배치 + ID 표)은 유지, 런타임 스포너만 새로 짠다. 1번으로 가도 챙길 것: ① 정책은 MonoBehaviour가 아니라 위치·반경 배열을 받는다(청크 스케일 테스트용 합성 좌표) ② 복제본 자식(17개 × 19) 정리 ③ 로드 시 검증 경고. 이 문서의 2~8절은 나중에 맵을 새로 만들거나 배치 방식을 바꿀 때의 참고로 남긴다.

2. 먼저 나눠 둘 것 — 저작과 런타임

저작 방식은 여러 가지여도, 런타임에 정책이 보는 형태는 하나여야 한다
그림 1 · 스포너의 네 질문 — 앞의 셋은 스포너, 마지막은 정책의 몫
이 문서의 관점 제안된 방법 1과 2는 사실 ② "어떤 자리에"를 누가 정하느냐의 차이다. 사람이 하나씩 찍느냐(1), 규칙이 생성하느냐(2). ③ 구성을 표로 둘지, ① 앵커를 어떻게 놓을지는 두 방법 모두에서 따로 고를 수 있다.

3. 제안된 두 방법

방법 1 = 지금 구조를 정리한 것 · 방법 2 = 포인트를 규칙으로 생성
그림 2 · 방법 1 (손 배치 + ID 표) 과 방법 2 (앵커 + 패턴)

방법 1 · 손 배치 + ID 표 (지금 구조를 정리한 형태)

씬에 스포너와 자식 포인트를 배치하고 spawnerId를 붙인다. 어떤 몬스터가 어느 포인트에 나오는지는 표(Excel → JSON)에 적고 DataManager가 읽는다.

장점
  • 위치를 완전히 통제 — 엄폐물 뒤, 길목처럼 지형 맥락을 살린 배치
  • 재현성이 가장 좋다 — 좌표가 고정이라 매번 같은 자리. 측정 비교에 유리
  • 구성은 표만 고치면 됨 — 밸런스 조정 때 씬을 열 필요 없음
  • 디버깅이 쉬움 — "1002번 3번 포인트"처럼 바로 짚을 수 있음
  • 기존 Excel → JSON → DataManager 파이프라인을 그대로 씀
단점
  • 배치 노가다 — 지금 669개. 복제본 17개 × 19개가 그 부작용
  • 정보가 두 곳에 나뉨 — id 오타, 자식 순서 변경, 인덱스 범위 초과가 조용히 틀어짐
  • 씬만 봐서는 무엇이 나오는지 모름 (표를 같이 봐야 함)
  • 포인트가 NavMesh 위인지 사람이 확인해야 함
  • 합성 스포너 N=10,000 같은 스케일 테스트용 데이터를 만들 수 없음

방법 2 · 앵커 + 패턴

씬에는 앵커만 놓고, 패턴(원형·사각형·격자 등)과 수치만 정한다. 포인트 좌표는 규칙으로 계산하고, 지형 위에 올리려면 NavMesh.SamplePosition으로 투영한다.

장점
  • 배치 비용이 스포너당 1번 — 669개가 23개로
  • 밀도·수를 숫자 하나로 조정 (count 17 → 12)
  • 데이터가 작고 사람이 읽기 쉬움
  • 합성 스포너를 코드로 찍어 낼 수 있음 → Phase 7 스케일 테스트와 잘 맞음
단점
  • 지형을 모름 — 벽 속·절벽·NavMesh 밖 포인트. 투영하면 포인트끼리 겹칠 수 있음
  • 규칙적인 모양이 인공적 (정확한 원형 진형) → 지터를 넣고 싶어짐
  • 지터·투영을 스폰할 때마다 하면 스폰 비용에 계산이 섞이고, 랜덤이면 재현성이 깨짐
  • 개별 포인트 예외("이 하나만 옮기고 싶다")를 표현 못 함
  • 복도·L자·다각형까지 가면 패턴 종류가 늘어 결국 에디터 도구가 됨

4. 실제로 쓰이는 다른 방식

③~⑤는 ② "어떤 자리에"의 다른 답, ⑥은 ③ "무엇을"의 답이라 어디에나 겹쳐 쓴다
③ 패턴 베이크 (방법 1 + 2 하이브리드)자리 생성은 규칙, 저장은 고정 좌표
구현 — 스포너 인스펙터의 "Bake" 버튼(에디터 스크립트)이 패턴으로 점을 만들고 NavMesh.SamplePosition으로 스냅한 뒤 Vector3[]로 직렬화. 기즈모로 미리보기. 손으로 옮긴 점은 override 표시 → 다시 베이크해도 보존
  • 장점 저작 비용은 방법 2, 런타임은 방법 1 — 좌표 고정이라 재현성·스폰 비용 순수성 둘 다
  • 장점 지형 검증을 베이크 시점에 1번. 예외 포인트도 표현 가능
  • 단점 에디터 도구를 만들어야 함. 지형을 고친 뒤 재베이크를 잊으면 옛 좌표가 남음 → 검증기 필요
  • 변형 에디터 베이크 대신 씬 로드 시 1회 해석도 가능 (패턴을 표에 두고 로드 때 계산·스냅). 스폰 때 계산만 안 하면 됨
④ 영역 + 수량 (런타임 샘플링)"이 구역에 RL 17마리 유지"
구현 — 볼륨(박스·폴리곤) + 목표 수. 부족하면 영역 안에서 무작위 점을 뽑아 SamplePosition, 서로 최소 거리를 두는 Poisson disk 샘플링을 흔히 씀. MMO 필드에서 자주 보는 형태
  • 장점 배치가 가장 적다 (영역 하나). 리스폰 위치가 매번 달라 반복감이 적음
  • 단점 재현성이 가장 나쁘다. 시드를 고정해도 난수 하나를 여러 스포너가 공유하면, 정책마다 스폰 순서가 달라서 받는 난수도 달라진다 (6절 그림 3)
  • 단점 스폰할 때마다 샘플링·투영 비용 → "스폰 1회 비용" 지표에 섞임
  • 비교 트랙 판정 측정용으로는 부적합. 쓰더라도 결과가 어느 방식에서든 같도록 고정 좌표로 풀어야 함
⑤ 팩(편대) 템플릿구성 + 상대 배치를 한 묶음으로 재사용
구현 — PackTemplateSO { slots: (offset, monsterId)[] }. 스포너는 템플릿 참조와 회전만 가짐. 액션 RPG의 "몬스터 팩" 개념과 같은 계열
  • 장점 "탱커 1 + 원거리 2" 같은 편대를 맵 전체에서 재사용 — 구성과 배치를 한 번에 수정
  • 장점 좌표가 템플릿에 고정이라 재현성 좋음
  • 단점 오프셋이 지형을 모름 (방법 2와 같은 문제) → 베이크나 스냅과 같이 써야 함
  • 판단 지금 필드는 RL 360 + AR 3으로 사실상 단일 종이라 템플릿의 이점이 작음. 몬스터 종류가 늘면 가치가 커짐
⑥ 슬롯 + 가중치 표 (구성 레이어)포인트는 역할만, 실제 몬스터는 표에서 뽑음
  • 장점 같은 배치로 맵·레벨·지역 변주. 배치와 구성이 완전히 분리됨
  • 단점 가중치 = 랜덤 → 측정할 때는 고정해야 함
  • 판단 ①~⑤ 어디에나 겹쳐 쓸 수 있는 층. 이번 비교에는 불필요, 나중에 확장 여지로만

⑦ 밀도 페인팅(지형에 밀도맵을 칠해 샘플링)은 오픈월드용이다. 범위를 일반 필드로 정했으므로 제외한다.

6. 비교 트랙이 스포너에 요구하는 것

어떤 저작 방식을 고르든 지켜야 Sector / 거리 / 청크 비교가 공정해진다
그림 3 · 난수를 공유하면 정책이 달라질 때 몬스터 자리도 달라진다
#요구이유

7. 제안 — 1과 2는 경쟁이 아니라 "포인트 생성기"의 두 종류

패턴 종류에 Manual(손 배치)을 넣으면 방법 1이 방법 2의 특수한 경우가 된다
그림 4 · 제안 구조 — 저작은 자유, 런타임은 하나
추천 — ③ 패턴 베이크 + 구성은 표 Manual / Circle / Rect / Grid 네 가지 패턴만 두고, 결과 좌표를 베이크해서 저장한다. 엄폐물 뒤처럼 자리를 꼭 지정해야 하는 곳은 Manual(= 방법 1), 넓은 공터는 Circle/Grid(= 방법 2). 구성(몬스터 × 수 · 리스폰)은 지금처럼 Excel → JSON 표에 두되, 포인트 인덱스 대신 "몬스터 × 수"로 적어 포인트 순서가 바뀌어도 데이터가 깨지지 않게 한다. 조인 오류는 R6 검증기가 에디터에서 잡는다.
이 추천이 푸는 것 노가다 (669 → 23 + 필요한 곳만 Manual) · 재현성 (좌표 고정) · 스폰 비용 순수성 (계산 없음) · 지형 안전 (베이크 시 스냅) · 스케일 테스트 (레코드를 코드로 생성) · 섹터 계층 의존 제거
대가 에디터 도구(베이크 버튼 · 기즈모 · 검증기)를 만드는 비용. 지형을 고친 뒤 재베이크를 잊는 위험 → 검증기가 "NavMesh 밖 포인트"로 잡음. 에디터 도구가 부담이면 변형안(로드 시 1회 해석)으로 시작해도 R1은 지켜진다.

{

    public SpawnPattern pattern;          // Manual | Circle | Rect | Grid

    [SerializeField] Vector3[] _bakedPoints; // [Bake] 결과 (Manual이면 자식에서 수집)
    [SerializeField] bool[] _overridden;    // 손으로 옮긴 점 — 재베이크해도 보존
}
