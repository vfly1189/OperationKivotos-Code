# 03. 최종 설계

## 0. 설계 원칙 — 층을 섞지 않는다

| 층 | 결정하는 것 | 기준 | 절대 하지 않는 것 |
|---|---|---|---|
| **②' 유예** | 지금 끄면 안 되는 대상 | 전투/어그로 상태 | — |
| **A. 존재** | 스폰 / 디스폰 | **절대 거리 임계값** | 품질은 안 건드림 |
| **B. 품질** | 틱 주기, 컴포넌트 on/off | **상대 순위 + 정원** | **절대 지우지 않음** |

> **A는 명단을 정하고, B는 그 명단 안에서 자원을 배분한다.**

### 왜 B가 지우면 안 되는가
B는 상대 평가다. **옆 몬스터가 몰려서 내 순위가 밀렸다는 이유로** 눈앞의 몬스터가 사라지면, 거리는 그대로인데 사라지는 것이라 플레이어에겐 ②의 경계 버그보다 더 황당하다.
존재 여부는 반드시 **플레이어가 예측 가능한 절대 기준(거리)** 에만 맡긴다.

---

## 1. ②' — 전투 유예 + 리쉬 복귀 (증상 봉합)

기존 섹터 구조를 유지한 채, **쓰고 있는 대상은 끄지 않는다**(참조 카운팅).

```
몬스터: 전투 시작 → 소유 스포너에 "사용 중" 등록
스포너: 사용 중인 몬스터가 있으면 비활성화 거부
플레이어가 멀어짐 → 몬스터가 원래 위치로 복귀(리쉬) → 등록 해제
사용 중 0 + 플레이어 없음 → 그때 비활성화
```

### 채택 조건 3가지 (없으면 사고 남)
1. **카운터(숫자)가 아니라 집합(HashSet)** 으로 관리하고, 주기적으로 죽은/null 항목을 청소
   → 통보 한 번 누락되면 조용히 새는 구조. [HP바 누수 사건](../TroubleShooting/MemoryLeak-MonsterHPBar/README.md)과 동일 계열
2. **유예 최대 시간**(예: 20초) 강제 — 상한이 없으면 최악의 경우 "전체 활성화"로 수렴
3. **유지 단위를 섹터가 아니라 스포너로** — 몬스터 1마리 때문에 섹터 전체가 켜져 있을 이유가 없음

### 위치
이것은 **최종안이 아니라 ②'** 다. 성능은 하나도 안 좋아진다(오히려 두 구역이 동시에 켜져 평균 활성 수는 늘어난다). 팝인도 그대로다.
**그러나 리쉬·전투 유예는 A층에서도 그대로 필요하므로 버리는 작업이 아니다.**

## 2. ① — 시뮬레이션 매니저 (제어점 확보)

```
[지금]                          [바꾼 뒤]
몬스터A.Update() → BT평가        MonsterSimulationManager
몬스터B.Update() → BT평가          └ 등록된 몬스터 리스트를 자기가 순회
몬스터C.Update() → BT평가              → 순서 / 빈도 / 개수를 통제
```

### 규칙
- 등록/해제는 `OnEnable`/`OnDisable` **대칭** + 매니저의 **주기적 청소** 병행
- 제거는 순회 중 즉시 하지 말고 **대기 큐**에 모았다가 순회 종료 후 일괄
- **경과 시간은 매니저가 주입한다** (`Time.deltaTime` 직접 사용 금지 — [04_Risks](04_Risks.md) 참고)
- **보스는 이관 대상 제외** (Timeline·Signal 결합)
- 데이터는 가능한 한 **배열 기반**으로 — 나중에 Job/Burst 확장 경로 확보

## 3. ②③ — 시간 분산 + 틱 그룹

```
60Hz 버킷 : 전투 중 / 화면 안
10Hz 버킷 : 근처, 비전투
 2Hz 버킷 : 멀리 (존재만)
```

- 같은 버킷 안에서도 **위상 오프셋**으로 프레임을 어긋내 스파이크 방지
- **핵심 규칙: "생각은 가끔, 움직임은 매 프레임."**
  목적지 결정만 저빈도로 하고 실제 이동·회전은 매 프레임 보간 → LOD 전환이 눈에 안 보임
- **승격은 즉시, 강등만 유예** — 피격/어그로 이벤트는 즉시 최고 등급으로

## 4. A층 — 거리 기반 존재 관리

### 왜 인접 섹터 그래프를 쓰지 않는가
1. **데이터가 썩는다** — 섹터를 옮기거나 추가할 때마다 이웃 목록을 손봐야 하고, 안 고치면 조용히 틀린다
2. **단위 크기가 안 맞는다** — 화면 25m인데 섹터 100m. 인접까지 켜면 낭비가 2~3배

→ 인접이라는 개념 자체가 필요 없다. **기하학에서 저절로 나온다.**

### 구현
`CullingGroup`에 **스포너(고정·불변)** 를 바운딩 스피어로 등록한다.
```csharp
group.SetBoundingSpheres(spawnerSpheres);        // 로드 시 1회. 스포너는 안 움직임
group.SetBoundingDistances(new[]{25f, 35f, 50f});
group.SetDistanceReferencePoint(playerTransform); // 카메라가 아니라 플레이어
group.onStateChanged += OnBandChanged;            // 폴링 없음
```

> ⚠ **몬스터가 아니라 스포너를 등록한다.** 몬스터는 죽고 풀을 오가서 인덱스가 불안정하다. 스포너는 영원히 안정적이다.

### 반경 산출 근거 (쿼터뷰라 계산 가능)
- `R_on` = 화면에 들어오는 최대 거리(≈25m) + 이동속도 × 프리페치 시간 → **약 35m**
- `R_off` = `R_on × 1.4` → **약 50m** (히스테리시스: 켜는 거리와 끄는 거리를 다르게)
- **제약**: `R_off` ≥ 최대 스킬 사거리 + 여유 (존재하지 않는 대상에게 스킬을 쏘는 상황 방지)

### 팝인 방지
`onStateChanged`가 주는 **`isVisible == false`일 때 우선 스폰/디스폰**한다.
(Unity 매뉴얼이 명시한 CullingGroup의 대표 용도)

### 예외
디스폰 금지는 개별 `if`로 흩뿌리지 말고 **`NeverDespawn` 플래그 하나로 통일**한다 (보스·네임드·퀘스트 대상).

## 5. B층 — 중요도 점수 + 예산 (조건부)

```
S = w1·(거리 감쇠)
  + w2·(화면에 보이는가)     ← A층이 이미 계산해 준 값 재사용
  + w3·(화면 차지 비중)
  + w4·(플레이어와 전투 중)   ← 하드 잠금 (아래 참고)
  + w5·(등급: 보스·네임드)

→ 점수 순 정렬 대신 **버킷 카운팅**(O(n))으로 커트라인만 찾음
→ 풀 시뮬 12마리 / 저빈도 25마리 / 나머지 정지
```

### 왜 조건부인가
쿼터뷰 카메라가 가까워(플레이어 뒤 5m) **"존재하지만 멀리 있는" 구간이 25m밖에 안 된다.** B가 차등을 매길 대상이 그 얇은 띠에만 있고, 스포너 밀도상 **평상시엔 예산이 안 차서 노는 시스템이 될 가능성이 높다.**

→ **A층 실측 데이터로 판단한다:**
> "35m 이내 몬스터 수"의 **최댓값**이
> - 10마리대에 머문다 → **B는 과잉설계.** 만들지 않는다 (그 판단 자체가 서사가 됨)
> - 30~40마리까지 튄다 → **B가 값을 한다.** 예산이 실제로 발동

### B의 진짜 가치 (성능 절감이 아님)
**A의 반경을 넓힐 자유.** A만 있으면 비용이 반경에 비례해 늘어 반경을 좁게 유지해야 하고, 좁으면 팝인이 생긴다.
B가 있으면 반경을 크게 잡아도 **비용에 상한이 걸린다** → 멀리 있는 몬스터가 이미 서 있는 게 보이고, 도망쳐도 안 사라지고, 원거리 저격이 된다.
즉 **"지금 것을 빠르게"가 아니라 "할 수 없던 것을 하게"** 한다.

### 필수 안전장치
- **전투 중이면 애니메이터·컴포넌트 강등 절대 금지** (하드 잠금 — 이유는 [04_Risks](04_Risks.md) 1번)
- 승격/강등 임계 분리 + **등급 변경 최소 유지 시간(dwell)** — 순위 흔들림에 의한 깜빡임 방지
- 단, **승격은 즉시**

## 6. Sector 볼륨의 새 역할

지우지 않는다. **성능 판정에서 손을 떼고 게임플레이 전용으로 남긴다.**

| 역할 | 담당 |
|---|---|
| 몬스터 활성화 (성능) | A층 (거리) |
| 구역 이름 표시 · BGM 전환 · 필드보스 | **Sector 볼륨** |
| 실내/미로 등 거리가 부적절한 구역 | Sector 볼륨으로 오버라이드 |

> "원래 다른 문제인데 한 시스템이 겸하고 있었다"를 분리한 것 자체가 설계 판단으로 제시할 수 있다.

### 거리 방식이 틀리는 경우 (정직하게 명시)
유클리드 거리는 **벽을 모른다.** 벽 하나 사이로 붙은 방은 직선거리 5m지만 실제로는 돌아가야 하는 먼 곳이다.
→ **야외 심리스 필드에 적합**하고, 실내·미로형에는 볼륨이 맞다. BackStreetMap은 전자에 해당.
