# 04. 예측되는 문제와 대응

> 설계 단계에서 막아야 하는 것과, 만들면서 대응해도 되는 것을 구분한다.
> 🔴는 **조용히 깨지는 것들** — 나중에 발견하면 원인 추적이 매우 어렵다.

---

## 🔴 치명적

### 1. `deltaTime` 오염
**증상**: 멀리 있는 몬스터의 공격 주기·대기 시간·쿨다운이 전부 느려진다. 가까이 가면 정상으로 돌아온다.
**원인**: BT가 `Time.deltaTime`으로 시간을 세는데 틱 간격을 5프레임에 한 번으로 바꾸면 **그 몬스터의 시간이 1/5 속도로 흐른다.**
**대응**: 매니저가 "지난 틱 이후 실제 경과 시간"을 주입하거나 절대 시각 기반으로 전환.
→ 어빌리티 Phase 1에서 쿨다운을 절대 시각으로 옮긴 것과 **동일 문제**. 그 경험을 재사용한다.

### 2. 애니메이터를 끄면 AbilitySystem이 멈춘다
**증상**: 몬스터가 공격 모션은 취하는데 데미지가 안 나가거나, 공격이 시작만 되고 안 끝난 채 굳는다. 에러·로그 없음.
**원인**: 어빌리티는 **애니메이션 이벤트(`AbilityBeat`)로 발사**된다. 애니메이터를 끄거나 컬링하면 이벤트가 안 뜬다.
**대응**: **전투 중(어그로)이면 애니메이터 강등 절대 금지.** 점수 가중치가 아니라 **하드 잠금**으로 취급.

### 3. 등록·해제 누락 = 유령 몬스터
**증상**: 매니저 리스트에는 있는데 오브젝트는 풀로 반환된 상태. 재사용된 인스턴스가 **이전 생애의 등록·티어를 물려받는다.**
**원인**: 풀링 구조 + 통보 기반 관리.
**대응**: `OnEnable` 등록 / `OnDisable` 해제 **대칭** + 매니저의 **주기적 청소**. 대칭만으로는 부족하다.
→ [HP바 누수 사건](../TroubleShooting/MemoryLeak-MonsterHPBar/README.md)과 같은 계열.

### 4. 순회 중 리스트 변경
**증상**: BT 평가 도중 몬스터가 죽어 리스트에서 빠지면 순회가 깨진다.
**대응**: 제거는 **대기 큐**에 모았다가 순회 종료 후 일괄 처리.

### 5. NavMeshAgent 소유권
**증상**: 티어 강등에서 `agent.enabled = false` 후 승격 시 위치가 튀거나 미끄러진다.
**대응**: [TransformOwnership 트러블슈팅](../TroubleShooting/TransformOwnership-NavMeshRigidbody/README.md)의 **"뺏기↔반납 대칭"** 규칙 재사용. 승격 시 `Warp` 필수.

### 6. CullingGroup 배열 참조 / 수명
**증상**: 배열을 갈아끼우면 댕글링, `Dispose` 누락 시 누수.
**대응**: **스포너(고정)만 등록**하여 인덱스를 영구 안정화. 씬 전환 시 Dispose를 리소스 수명 체계에 편입.

## 🟠 게임플레이가 이상해지는 것

### 7. LOD 전환이 눈에 보인다
틱을 낮추면 방향 전환이 뚝뚝 끊긴다. 쿼터뷰는 카메라가 가까워 **티어 경계가 화면 안에 들어올 수 있다.**
→ **"생각은 가끔, 움직임은 매 프레임."** 목적지 결정만 저빈도, 이동·회전은 매 프레임 보간.

### 8. 화면 밖 몬스터를 때리면 반응이 늦다
원거리 무기로 저티어 몬스터를 맞히면 "때렸는데 안 아파함".
→ 피격/어그로는 **즉시 승격**. 깜빡임 방지용 dwell time을 **승격에는 걸지 않는다.**

### 9. 스킬 사거리 > 디스폰 반경
존재하지 않는 몬스터에게 스킬을 쏘게 된다.
→ **설계 제약으로 명시**: 디스폰 반경 ≥ 최대 스킬 사거리 + 여유.

### 10. 팝인
거리 기반은 다가가며 몬스터가 순차적으로 나타난다. 반경이 화면보다 충분히 크지 않으면 **화면 가장자리에서 튀어나오는 게 보인다.**
→ `isVisible == false`일 때 우선 스폰 (CullingGroup 활용).

### 11. 예외 플래그 번식
보스 금지, 퀘스트 몬스터 금지, 소환수는? 이벤트 몬스터는? — A층의 단순함이 갉아먹힌다.
→ **`NeverDespawn` 플래그 하나로 통일.**

### 12. 리스폰 타이머 정책 미정
멀리서 죽인 몬스터의 타이머가 도는 중에 스포너가 비활성화되면? 계속 돌릴지, 멈출지, 복귀 시 즉시 리젠할지.
→ 결정 필요. MMO 방식(최소시간 + 변동폭, 위치·방향 랜덤)도 함께 검토.

### 13. 반응 지연
5프레임에 한 번이면 최대 83ms 지연. 전투 중엔 체감된다.
→ 전투 중은 무조건 60Hz 버킷.

## 🟡 기술적으로 물리는 것

### 14. 연출 카메라 전환
보스 Timeline·승리 연출에서 카메라가 바뀌면 가시성 판정이 요동친다.
→ 거리 기준점은 **플레이어로 고정**, 가시성만 카메라 참조. 연출 중에는 시스템 일시 정지.

### 15. 실행 순서 변경으로 인한 타이밍 버그
Unity는 Update 호출 순서를 **보장하지 않는다.** 매니저로 옮기면 순서가 고정되는데, 이때 플레이어·카메라와의 상대 순서가 바뀌며 1프레임 어긋남이 생길 수 있다. 미묘하고 찾기 어렵다.
→ 기존 `Managers.Update()` 흐름 안에 **명시적 위치**로 배치.

### 16. 프로파일러에서 뭉쳐 보인다
전부 `MonsterSimulationManager.Update` 하나로 합쳐져 어느 몬스터가 비싼지 안 보인다.
→ 커스텀 `ProfilerMarker` 삽입. **오히려 계측 자산이 된다.**

### 17. 보스는 이관하지 않는다
Timeline + Signal + BT 결합. 여기까지 끌어오면 회귀 위험이 급증한다.
→ **일반 몬스터만 이관.** 범위를 명시적으로 자른다.

### 18. 디버그 뷰가 없으면 개발이 안 굴러간다
"저 몬스터가 왜 안 움직이지?"의 원인이 A인지 B인지 예산인지 구분 불가.
→ **몬스터 머리 위에 티어·점수 표시하는 디버그 뷰는 선택이 아니라 필수 인프라.** 그 화면이 그대로 포트폴리오 스크린샷이 된다.

## ⚫ 포트폴리오 리스크

### 19. ①(매니저 이관)만으로는 수치가 안 나온다 ★
Update를 옮기는 것 자체는 성능이 거의 안 변한다. "리팩터만 하고 개선 수치가 없다"가 될 수 있다.
→ **①을 단독 성과로 제시하지 말 것.** "제어점 확보 → ②③ 적용 → 이만큼 줄었다"로 **묶어서** 제시한다. ①은 수단이지 성과가 아니다.

### 20. B의 효과가 A에 묻힐 수 있다 ★★
A만 해도 절감의 대부분이 나올 가능성이 높다. 그러면 B는 **복잡도만 늘리고 수치는 안 나오는** 결과가 된다.
→ **처음부터 조건을 분리해 측정한다.** ([05_Roadmap](05_Roadmap.md) 측정 계획)
→ 그리고 **B가 빛나는 무대는 평상시가 아니라 몹 몰이 상황**임을 분명히 한다. 평상시엔 A가 주역, 최악에선 B가 주역.

### 21. Update 매니저 자체는 흔한 패턴이다
이것만 얘기하면 "튜토리얼에서 본 것"으로 보인다.
→ **차별점은 매니저가 아니라 그 위에 얹은 정책**(틱 그룹 + 거리 밴드 + 예산). 매니저는 무대, 정책이 공연. 발표 비중을 그렇게 배분한다.

### 22. 규모가 작아 과잉설계로 보일 수 있다
스포너 23개, 활성 60마리.
→ **"필요해서 만든 게 아니라, 이 구조가 규모에 어떻게 반응하는지 확인하려고 만들었고 그 경계를 측정했다"** 로 답한다. 억지로 "필요했다"고 하면 되치기당한다.

### 23. 일정 리스크
어빌리티 Phase 1이 main 미머지, Phase 2 미완 상태에서 또 하나의 큰 리팩터가 들어간다.
→ 기술 리스크가 아니라 **"완성된 게 하나도 없는 상태"** 의 위험. 단계마다 완결 지점을 두고 멈출 수 있게 설계한다.
