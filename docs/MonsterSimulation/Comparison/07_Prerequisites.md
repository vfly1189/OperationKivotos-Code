# 07. 사전 작업 — 통제 변수 확보

> 작성: 2026-08-22
> 5가지 방법을 재기 **전에** 끝내야 하는 것들.
> 방법의 우열이 아니라 **측정의 유효성**에 관한 문서다.

## 0. 판단 기준 한 줄

> **이걸 고치면 5가지 방법의 상대 순위가 바뀌나?**

바뀌면 통제 변수라 **재기 전에** 고친다. 안 바뀌면 나중에 해도 된다.

[02_Measurement](02_Measurement.md) 0절의 "재고 나서 고친다"는 **비교 대상(5가지 방법)** 에 대한
원칙이고, 하네스와 통제 변수는 그 원칙의 *전제*다. 충돌하지 않는다.

## 1. 현황 실측 (2026-08-22)

추정이 아니라 `SpawnerData.json`과 `BackStreetMap.prefab`을 직접 파싱해 집계한 값이다.

### 1.1 섹터별 몬스터 수

| 섹터 | 2000 (AR) | 2001 (RL) | 합 |
|---|---|---|---|
| 1 | – | 102 | 102 |
| 2 | – | 68 | 68 |
| 3 | 3 | 3 | 6 |
| 4 | – | **119** | **119** |
| 5 | – | 68 | 68 |
| **맵 전체** | 3 | 360 | **363** |

한 번에 한 섹터만 활성이므로(`ActivateAllSectors`는 `BenchmarkTester` 전용)
**동시 최대치는 2000 → 3, 2001 → 119, 2002(Tank) → 0.**

섹터별 편차가 6 ~ 119로 20배다. 스포너 내부 구성을 균일하게 가져가도
**섹터 수준에서 밀도 변량이 이미 확보되어 있다.**

### 1.2 풀 프리워밍과의 불일치 ★

[GameScene.cs:108](../../../Assets/Scripts/Scenes/GameScene/GameScene.cs:108)의 `CreatePool()`은
세 종류를 **30개씩** 하드코딩한다.

| 몬스터 | 프리워밍 | 실제 최대 필요 | 결과 |
|---|---|---|---|
| 2000 AR | 30 | 3 | 27개 낭비 |
| 2001 RL | 30 | **119** | **게임 중 89회 추가 `Instantiate`** |
| 2002 Tank | 30 | **0** | 인스턴스 30개 + 프리팹 핸들 전부 낭비 |

**이것이 측정을 직접 오염시킨다.** `PoolManager.Pop`은 스택이 비면 그 자리에서
`Object.Instantiate`를 하고 **로그를 남기지 않는다**
([PoolManager.cs:151](../../../Assets/Scripts/Managers/Core/PoolManager.cs:151)).
그 비용이 그대로 `>33ms` 히칭 프레임으로 잡힌다.
히칭 프레임 수는 [02_Measurement](02_Measurement.md) 4절의 **핵심 지표**다.

그리고 이 오염은 **방법마다 다르게 낀다** (스폰 빈도가 방법별로 다르므로 → 3.2).
모든 방법에 균일하게 끼는 노이즈가 아니라 **순위를 바꾸는 노이즈**다.

### 1.3 프리팹의 죽은 스폰 포인트

23개 스포너 중 **18개가 자식 Transform을 34개씩** 갖고 있으나 데이터는 17개만 쓴다.
**306개가 사용되지 않는다.**

더 나쁜 것은 개수가 아니라 **위치의 정체성이 하이어라키 순서에 있다는 것**이다.
`pointIndex: 5`가 어디인지는 프리팹 자식 정렬 순서를 봐야만 알 수 있고,
자식을 하나 끼워넣거나 지우면 전체가 조용히 밀린다.
반대 방향 불일치(데이터가 더 많이 요구)는
[MonsterSpawner.cs:38](../../../Assets/Scripts/Managers/Core/SectorManager/MonsterSpawner.cs:38)의
`continue`가 **로그 없이** 삼킨다.

→ 실험 중에는 배치를 바꾸지 않으므로 직접적인 해는 없다.
다만 **통제 변수가 관측 불가능한 상태**이므로 최소 조치가 필요하다 (→ 2.4).

## 2. 해야 할 것

### 2.1 몬스터 생명주기 계약 · 3~4일

> **상세판: [Audit/Lifecycle.md](../Audit/Lifecycle.md)** (2026-08-25)
> — Awake/Start 훅 의미론, 이 계약에서 따라나오는 불변식, 현재 코드 판정 L0~L7.
> 아래 표와 목표 순서는 그대로 유효하다.

풀에서 꺼낸 객체는 `Awake`가 돌지 않는다. 지금 그 계약이 코드에 명시되어 있지 않다.

| 훅 | 성격 | 담을 것 |
|---|---|---|
| `Awake` | 인스턴스당 1회 (풀 생성 시점) | 컴포넌트 캐시, BT 구축, `EnsureOn` |
| **`OnSpawn(ctx)`** | 매 스폰. **비활성 상태에서 호출** | 스탯 주입 후 상태·타겟·쿨·BT 리셋 |
| `OnEnable` | 활성화 반응만 | Animator 등 활성 상태를 요구하는 것만 |
| **`OnDespawn()`** | 매 디스폰 | 구독 해제, HP바 반납, CTS 취소 |

**활성화 순서를 뒤집는 것이 핵심이다.** 현재:

```
SetActive(true)                              ← ResourceManager.cs:406
  → BMC.OnEnable → HealthComp.Recover()      ← MaxHp가 아직 이전 생애 값 (BMC.cs:87)
  → NMC.OnEnable → HP바 생성 시작             ← 스탯 주입 전
그 다음에야 → MonsterFactory.cs:48 SetStat() → 다시 Recover()
```

`ResourceManager.Instantiate`가 마지막에 `SetActive(true)`를 해버려서
팩토리가 그 사이에 끼어들 수 없다. **`activate: false` 오버로드가 그 이음새다.**

목표 순서:

```
Pool.Pop()            → 비활성 인스턴스
transform.position    → agent 안 건드리고 위치만
Stat.SetStat(...)     → 데이터 주입
ctrl.OnSpawn(ctx)     → 상태 리셋
SetActive(true)       → 이제서야 OnEnable
```

부수 효과 — 비활성 상태에서 `transform.position`으로 옮겨두면
[ResourceManager.cs:393](../../../Assets/Scripts/Managers/Core/Resource/ResourceManager.cs:393)의
`agent.Warp` 분기가 불필요해진다. NavMeshAgent는 켜질 때 자기 위치 기준으로 NavMesh에 스냅한다.
(현재는 `PoolManager.Pop`이 끈 agent에 `Warp`를 호출하고 있어 **위치가 반영되지 않을 수 있다 — 검증 필요**)

관련 감사 항목: [Audit/Issues.md](../Audit/Issues.md) M5(상태를 가진 BT 노드) · M3(스폰 1프레임 내 사망) · M6(보스 연출 플래그)

### 2.2 풀 용량을 외부에서 주입 · 2.1과 함께

- `CreatePool(prefab, key, count)`의 `count`가 하드코딩이 아니라 **호출자가 계산한 값**이 되게
  - 스트레스 씬 → 하네스 파라미터
  - 실제 맵 → 스포너 데이터 집계 (7단계)
- **`Pop`이 풀을 즉석 생성하면 개발 빌드 경고** ★
  - 이게 있어야 "사전 할당이 실제로 다 덮었나"를 검증할 수 있다
  - **경고 0인 조건에서만 측정을 채택한다**
  - `[PoolLeak]` 경고와 같은 계열

### 2.3 스포너 소유권 · 2~3일

[01_Methods](01_Methods.md) 방법4의 구현 판단 4번("디스폰돼도 리스폰 타이머는 스포너가 소유")이
**현재 코드로는 표현 불가능하다.**

리스폰이 죽은 몬스터의 `OnDespawned` 람다에 걸려 있고
([MonsterSpawner.cs:176](../../../Assets/Scripts/Managers/Core/SectorManager/MonsterSpawner.cs:176)),
[BaseMonsterController.cs:85](../../../Assets/Scripts/Controllers/Monster/BaseMonsterController.cs:85)의
`OnDespawned = null`이 그것을 지운다. 즉 **리스폰 상태가 몬스터 인스턴스에 얹혀 있어**
디스폰하면 같이 사라진다. 밴드 밖으로 나갔다 돌아오면
"부활 대기 중이던 포인트"가 그냥 살아있는 상태로 리셋된다.

- 포인트별 상태(살아있음 / T초 뒤 부활 예정 / 비어있음)를
  **몬스터 인스턴스와 독립적으로** 스포너가 소유
- 소유 범위를 "스폰 ~ **디스폰 완료**"까지로
  (현재는 [MonsterSpawner.cs:165](../../../Assets/Scripts/Managers/Core/SectorManager/MonsterSpawner.cs:165)에서
  사망 즉시 목록에서 빼므로 디스폰 연출 2초 동안 소유가 끊긴다 → 평균/최대 활성 수 지표가 흔들린다)

관련 감사 항목: [Audit/Issues.md](../Audit/Issues.md) S1 · S2 · S3

### 2.4 최소 조치 두 가지 · 각 30분

## 3. 하지 않는 것

### 3.1 스포너 배치 리팩터 (앵커 + 패턴)

프리팹에 앵커 위치만 두고 런타임에 패턴(Ring / Grid / Line / Scatter)으로 배치하는 방식을 검토했다.
`pointIndex`의 하이어라키 순서 결합이 사라지고 306개 죽은 오브젝트도 없어지므로
**배치의 유지보수성은 분명히 개선된다.** 그러나 **실험 경로에는 넣지 않는다.**

1. 스트레스 씬은 스포너를 **코드로 생성**하므로 맵 프리팹 배치를 우회한다
2. 비교 트랙 동안 배치를 바꿀 일이 없다 → **이득이 발생하지 않는 시점에 비용을 내는 셈**
3. 실험 중에 배치가 바뀌면 **그 전 측정치가 전부 무효**가 된다

→ 결론 적용 단계(4절 7번)로 미룬다. 그때는 실제 맵을 손대야 하므로 필요해진다.
306개 죽은 오브젝트도 그때 정리한다.

**채택 시 필수 조건 3가지** (미래의 나에게):
`NavMesh.SamplePosition` 스냅 + 실패 포인트 폐기 / `OnSceneGUI` 패턴 프리뷰
(없으면 배치가 깜깜이가 되어 지금보다 나빠진다) / 수동 오버라이드로 도망가지 말고 앵커를 잘게 쪼갤 것.

### 3.2 다만 알고 갈 것 — 스폰 비용은 방법4에 불리하게 작용한다 ★

| 방법 | 스폰/디스폰 빈도 |
|---|---|
| 1 전부 | 시작 1회, 이후 0 |
| 2 구역 | 섹터 전환마다 일괄 |
| 3 구역+예외 | 방법2 + 유예 |
| **4 거리** | **밴드를 넘나들 때마다. 압도적으로 많음** |
| 5 느리게 | 0 |

스폰 1회가 비싸면 방법4가 손해를 본다. 그런데 그것은
**"거리 기반 방식의 본질적 비용"이 아니라 "내 스폰 구현의 비용"** 이다.
둘을 분리하지 못하면 [04_Comparison](04_Comparison.md)의 결론이 구현 품질에 흔들린다.

특히 현재 스폰 1회에는 **HP바 UI 생성**(`MakeSubItemAsync`, 비동기 로드)이 들어 있고
사망마다 버려진다. 방법4에서는 이것이 계속 돈다.

→ 그래서 지표에 **스폰/디스폰 횟수**와 **스폰 1회 평균 비용**을 넣는다
([02_Measurement](02_Measurement.md) 4절). 방법4가 졌을 때 원인을 표에서 가를 수 있어야 한다.

## 4. 순서와 근거

| | 할 일 | 왜 이 자리 | 대략 |
|---|---|---|---|
| **0** | 문서 갱신 + **예측 박제** | 지표가 정해져야 하네스가 뭘 수집할지 정해진다. **예측은 구현 전에 써야 순수하다** | 반나절 |
| **0.5** | 경계 소실 Before 영상 | 방법3을 만들면 다시 못 찍는다 ([README](README.md) ⚠) | 30분 |
| **1** | 생명주기 + 풀링 (2.1 · 2.2) | 통제 변수. 안 하면 히칭 지표가 풀 부족을 잰다 | 3~4일 |
| **2** | 스포너 소유권 (2.3 · 2.4) | 방법4의 전제 조건 | 2~3일 |
| **3** | 측정 하네스 | 방법 구현 **전** | 1주 |
| **4** | 기준선 측정 (방법1 · 2) | 이미 있는 둘로 **하네스 자체를 검증** | 1~2일 |
| **5** | 방법3 → 4 → 5 | | 3~4주 |
| **6** | 전 조합 측정 + 표 + 예측 대조 | | 3~4일 |
| **7** | 결론을 실제 맵에 적용 + 재검증 | 여기서 배치 리팩터·맵 단위 풀 예산이 필요해진다 | 1주 |

**0번이 지금 당장인 이유**: 예측 박제는 구현 전에 써야 값이 있다.
방법4를 만들다 보면 결과가 보이기 시작하고, 그 뒤에 쓴 예측은 예측이 아니다.
비용은 반나절인데 나중에는 절대 복구되지 않는다. 0.5번 영상도 같은 성격이다.

**4번의 이유**: 하네스에 버그가 있는 채로 방법3~5를 다 만들고 나서 발견하면 전 조합을 다시 돌려야 한다.
이미 동작을 아는 두 방법으로 하네스를 먼저 검증한다.

**7번의 이유**: 이것이 없으면 "스트레스 씬에서 벤치마크를 돌렸다"로 끝나고
실제 게임은 여전히 방법2로 돌아간다. 덤으로
**"합성 벤치마크가 실제 배치에서도 맞았나"** 라는 자체 검증이 나온다.
