# 01. 5가지 방법 정의

## 0. 전제 — 게임플레이 방식을 하나로 고정한다

| 항목 | 값 |
|---|---|
| 맵 | 끊기지 않는 **하나의 연속된 야외 필드** (로스트아크형) |
| 몬스터 | 스포너가 맵 곳곳에 산재. **개체가 아니라 3~17마리 무리 단위로 배치** |
| 시야 | 타이트 쿼터뷰. 화면에 들어오는 지면 **약 25m** (실측: `CameraController._delta = (0,4,-5)`) |
| 카메라 | **각도 고정.** 회전·피치 변화 없음 |
| 지형 | **고도차 없음.** 맵 전체가 사실상 평면 |
| 현재 규모 | Sector 5개 / MonsterSpawner 23개 / 몬스터 363마리 (`BackStreetMap.prefab`) |
| 동시 최대 | **한 섹터만 활성 → 119마리** (섹터별 6 / 68 / 102 / 119 / 68) |

전제를 고정하면 "실내 던전이면 어떤가" 같은 곁가지가 잘리고, 5가지가 **같은 조건에서 정면으로** 붙는다.
(조건이 바뀌면 답이 바뀐다는 이야기는 결론부에서 한 번만 다룬다. → 05_PortfolioNarrative(비공개))

## 0.1 쿼터뷰 · 단일 맵이 만드는 조건 ★

**이 조건들이 5가지의 우열을 실제로 좌우한다.** 오픈월드 크라우드(→ [06_References](06_References.md) Mass AI)와
정면으로 갈리는 지점이므로 인용보다 먼저 밝힌다.

| # | 조건 | 결과 |
|---|---|---|
| 1 | **오클루전이 거의 없다** | 위에서 내려다보므로 화면 안 = 거의 다 보임. "안 보이니까 끈다"는 렌더 최적화 여지가 구조적으로 적고, **시뮬레이션 최적화의 상대 비중이 커진다** |
| 2 | **시야가 고정 크기 상수 영역** | 카메라 각도가 안 변하므로 "플레이어 중심 반경 R" = 시야. **거리 기반(방법4)이 이론적으로 정확히 맞는 구조** — 자유 카메라 3D였다면 거리만으로 부족하다 |
| 3 | **화면 내 개체 수에 구조적 상한이 있다** | 화면 면적이 상수 × 밀도가 일정 → **총량과 무관하게 상수.** 실제 상용 게임의 맵 총량이 수백에서 멈추는 이유 |
| 4 | **그 대신 팝인이 더 잘 보인다** | 화면 가장자리가 항상 같은 거리에 있어 밴드 경계가 겹치면 매번 같은 자리에서 튄다. **체감 지표가 이 장르에서 더 중요해지는 근거** |
| 5 | **공간 분할이 2D로 충분** | 고도차가 없으므로 옥트리 불필요. 쉬운 문제를 푼 것이 아니라 **조건을 보고 자료구조를 고른 것**으로 기술한다 |
| 6 | **무리 단위 배치** | 개체가 아니라 무리로 판정하는 것이 자연스럽다. **방법4가 몬스터가 아니라 스포너를 등록하는 근거** (스피어 수가 개체 수의 1/10~1/20) |
| 7 | **밀집이 예외가 아니라 기본 플레이 패턴** | 유인해서 광역기로 쓸어담는 것이 이 장르의 정상 플레이. NavMeshAgent 회피는 이웃 수에 비선형이라 **밀집이 주된 비용 후보** |
| 8 | **이펙트·투사체가 몹보다 비쌀 수 있다** | 프레임이 실제로 떨어지는 순간은 몹이 많을 때가 아니라 스킬이 터질 때. 밀집 측정이 곧 **AbilitySystem 부하 측정**이 된다 |

### 여기서 나오는 축 우선순위 ★

3번 때문에 **총량(N)은 이 장르의 1차 변수가 아니다.** 7번 때문에 **밀도가 1차 변수다.**
측정 축을 그렇게 잡는다 → [02_Measurement](02_Measurement.md) 3절.

> **"3000마리를 돌릴 일 없지 않나요?"**
> 없다. 그런데 **왜 없냐면**, 화면에 보이는 만큼만 도는 구조면 총량이 몇이든 상관없어서
> 총량을 늘릴 이유가 없기 때문이다. 반대로 총량에 비례하는 구조면 레벨 디자이너가
> 몹을 더 놓고 싶을 때마다 성능 협상을 해야 한다.
> **N=3000은 그 차이를 드러내려고 넣은 극한값이지 목표 시나리오가 아니다.**

## 0.2 5가지는 임의의 후보가 아니다 — 한 축 위의 네 점 + 직교하는 하나

```
[존재 축] 누구를 존재하게 할 것인가 — 판정 단위가 화면 크기까지 내려온다

방법1          방법2           방법3            방법4
맵 전체   →   구역 100m   →   구역 + 예외   →   반경 약 45m
 (∞)                                            ↑ 화면 지면 ~25m

[품질 축] 존재하는 것을 얼마나 자주 돌릴 것인가  ← 직교
방법5   끄지 않고 틱 등급만 강등
```

방법1~4는 전부 **"누가 존재하는가"** 를 정하는 방식이고 다른 건 판정 단위 하나뿐이다.
방법5만 축이 다르므로 **방법4와 동시에 적용할 수 있다.** 이게 결론의 뼈대다.

## 방법 1 — 전부 켜두기

**분류**: 없음 (관리 부재) · **상태**: 이미 있음 (`BenchmarkTester` F1) · **서사 내 위치**: 표의 상한선

### 동작
아무것도 하지 않는다. 시작 시 모든 스포너가 몬스터를 뽑고, 그 몬스터들은 종료까지 계속 돈다.

### 좋은 점
- 코드가 0줄. 버그가 생길 구석이 없다
- 몬스터가 사라지거나 튀어나오는 일이 절대 없다
- **몬스터가 수십 마리 규모면 이게 정답이다** — 관리 비용이 이득보다 크다

### 나쁜 점
- 비용이 전체 몬스터 수 N에 그대로 비례한다
- 화면 반대편 몬스터도 전부 계산한다. 순수 낭비
- 메모리를 최대로 쓴다

### 주의
현재 포트폴리오의 Before 수치가 이것(F1)인데, **아무도 이 구성으로 출시하지 않으므로 Before로는 약하다.**
그래서 서사의 출발점에서 빼고 표의 상한선으로만 남긴다.

## 방법 2 — 구역 하나만 켜두기

**분류**: **Zone-based interest management** · **상태**: 구현되어 있음 (현재 방식) · **서사 내 위치**: 출발점

### 동작
맵에 트리거 볼륨(Sector)을 5개 놓는다. 플레이어가 진입하면 그 구역 스포너를 전부 `SpawnMonsters()`,
이전 구역은 전부 `DespawnMonsters()`.

실물: [Sector.cs](../../../Assets/Scripts/Managers/Core/SectorManager/Sector.cs) ·
[SectorManager.cs](../../../Assets/Scripts/Managers/Core/SectorManager/SectorManager.cs) ·
[MonsterSpawner.cs](../../../Assets/Scripts/Managers/Core/SectorManager/MonsterSpawner.cs)

### 좋은 점
- 단번에 크게 가벼워진다
- 구현이 쉽다. 볼륨 놓고 진입만 감지하면 된다

### 나쁜 점
- **G1 — 경계에서 때리던 몬스터가 사라진다.** 구역을 넘는 순간 이전 구역이 통째로 꺼진다.
  `Sector.OnTriggerExit`은 **빈 몸통**이다
- **G3 — 진입 프레임에 스폰이 몰린다.** `spawnList`를 순회하며 모든 UniTask를 즉시 `Forget()`. 프레임 예산이 없다
- **G2 — 판정 단위가 화면보다 크다.** 구역 100m vs 화면 25m. 지금도 화면 밖을 대량으로 켜고 있다
- **G4 — 메모리는 안 준다.** 디스폰 = `Pool.Push`. 풀이 `AcquirePoolRef`로 프리팹 핸들 refCount 티켓을 계속 쥔다
- 맵이 커지면 구역도 커져서 다시 무거워진다. **N에 대한 기울기는 방법1과 같고 상수배만 나아진 것**

### 수치 주의
"5구역이니 5분의 1"은 **틀리다.** 몬스터가 구역마다 고르게 있지 않다.
기존 실측은 F1 대비 **▼57%** 이므로, 문서·슬라이드에는 실측값을 쓴다.

## 방법 3 — 구역을 켜되, 싸우는 대상은 예외

**분류**: Hybrid (zone + 참조 카운팅) · **상태**: 미구현 · **서사 내 위치**: 전환점 (일부러 실패하는 단계)

### 동작
```
몬스터가 전투 시작 → 소유 스포너에 "사용 중" 등록
스포너: 사용 중인 몬스터가 하나라도 있으면 비활성화 거부
플레이어가 멀어짐 → 몬스터가 원래 위치로 복귀(리쉬) → 등록 해제
사용 중 0 + 플레이어 없음 → 그때 비활성화
```

### 채택 조건 3가지 (없으면 사고 난다)
1. **카운터(int)가 아니라 집합(HashSet)** + 주기적으로 죽은/null 항목 청소
   → 통보를 한 번 놓치면 조용히 새는 구조. [HP바 누수 사건](../../TroubleShooting/MemoryLeak-MonsterHPBar/README.md)과 동일 계열
2. **유예 최대 시간(예: 20초) 강제** — 상한이 없으면 경계에 붙어 계속 싸울 때 **방법1로 수렴한다**
3. **유지 단위를 섹터가 아니라 스포너로** — 한 마리 때문에 구역 전체가 켜져 있을 이유가 없다

### 좋은 점
- **G1(경계 소실)이 완전히 사라진다.** 이게 목적이다
- 기존 구역 구조를 건드리지 않아도 된다
- 여기서 만드는 **리쉬 복귀는 방법4에서도 그대로 쓴다.** 버리는 작업이 아니다

### 나쁜 점
- **성능이 좋아지지 않는다.** 두 구역이 동시에 켜져 있는 시간이 생기므로 평균 활성 수가 늘어난다
- G2(낭비) · G3(진입 히치) · G4(메모리)는 하나도 안 고쳐진다
- 최악의 경우(경계에서 계속 전투) **방법1로 수렴한다**

### 표현 주의 ★
"성능이 **나빠진다**"고 단정하지 말 것. 경계 전투는 상시가 아니라서 **실측은 방법2와 비슷하게 나올 수 있다.**
서사가 "3번이 성능을 되돌려놓는다"에 걸리면 측정 결과에 따라 무너진다.
측정과 무관하게 확실히 참인 것만 주장한다 → **"버그는 고쳤지만 성능은 조금도 좋아지지 않았고, 최악의 경우
방법1로 수렴한다."** 실제로 나빠지면 그때 수치를 근거로 강하게 쓰면 된다.

## 방법 4 — 내 주변 거리로만 판단

**분류**: **Aura-based interest management** · **상태**: 미구현 · **서사 내 위치**: 본론

### 동작
```csharp
group.SetBoundingSpheres(spawnerSpheres);         // 로드 시 1회. 스포너는 안 움직임
group.SetBoundingDistances(new[]{ 25f, 35f, 50f });
group.SetDistanceReferencePoint(playerTransform); // 카메라가 아니라 플레이어
group.onStateChanged += OnBandChanged;            // 폴링 없음
```
구역·경계·인접이라는 개념 자체가 사라진다. 기하학에서 저절로 나온다.

### 구현 판단 4가지 — **슬라이드에 들어갈 알맹이는 이론이 아니라 여기다**

| 판단 | 이유 |
|---|---|
| 몬스터가 아니라 **스포너**를 등록 | 스포너는 안 움직이므로 스피어 갱신 비용 0. 몬스터를 등록하면 매 프레임 위치를 다시 써야 함 |
| 기준점 = 카메라가 아니라 **플레이어** | 카메라 회전만으로 세계가 스폰/디스폰되면 안 됨 |
| 밴드 경계에 **히스테리시스** | 안 넣으면 경계선 위에서 왕복할 때 깜빡임. 방법3이 고쳤던 문제가 다른 얼굴로 돌아옴 |
| 디스폰돼도 **리스폰 타이머는 스포너가 소유** | 화면 밖 세계가 멈추지 않음. 대표값 시뮬레이션 |

### 좋은 점
- **경계가 존재하지 않으므로 경계 버그도 없다.** 고친 게 아니라 없앤 것
- 화면에 보이는 만큼만 켠다. 낭비 최소
- **맵이 커져도 활성 개체 수가 늘지 않는다** (밀도가 일정하다는 전제). 방법2가 상수배 개선인 데 반해 **점근적 개선**
- 안 쓰는 몬스터를 실제로 지우므로 **메모리를 줄일 여지가 생긴다**

### 나쁜 점
- 팝인 — 멀리 있던 몬스터가 밴드에 들어오면 없다가 생긴다
- 밴드 경계 깜빡임 (히스테리시스로 막는다)
- **밀집에 무력하다.** 몬스터가 한곳에 몰리면 전부 밴드 안이라 걸러낼 게 없다 → 방법5가 필요한 이유

### 메모리 조건 ★
**방법4만 해서는 메모리가 줄지 않는다.** 디스폰이 `Pool.Push`에서 끝나고 풀이 프리팹 핸들 티켓을
계속 쥐고 있기 때문(G4). **풀·핸들 반납 정책을 같이 고쳐야** 실제 MB가 떨어진다.
이 조건을 명시하는 것이 오히려 이득이다 — Addressable 리소스 파트로 연결되는 고리가 여기서 생긴다.

### 완전 상수가 아니라는 단서
CullingGroup도 스포너 수만큼 스피어를 돈다. 다만 개체당 AI 비용보다 2~3자릿수 싸서 곡선이 평평해 보일 뿐이다.
이 단서를 직접 다는 편이 신뢰를 준다.

## 방법 5 — 끄지 않고, 대신 느리게

**분류**: **Significance / LOD 기반** (UE `Significance Manager`, `Mass AI` 계열) · **상태**: 미구현 ·
**서사 내 위치**: 축이 다른 보완재

### 동작
```
60Hz 버킷 : 전투 중 / 화면 안
10Hz 버킷 : 근처, 비전투
 2Hz 버킷 : 멀리 (존재만)
```
- 같은 버킷 안에서도 **위상 오프셋**으로 프레임을 어긋내 스파이크 방지
- **"생각은 가끔, 움직임은 매 프레임."** 목적지 결정만 저빈도로 하고 이동·회전은 매 프레임 보간
  → 등급 전환이 눈에 안 보인다
- **승격은 즉시, 강등만 유예** — 피격·어그로는 즉시 최고 등급으로

### 전제 작업
몬스터가 저마다 `Update()`에서 `_topNode.Evaluate()`를 도는 구조를 먼저 걷어내야 한다
([BaseMonsterController.cs:99](../../../Assets/Scripts/Controllers/Monster/BaseMonsterController.cs:99)).
= 시뮬레이션 매니저(제어점) 확보. 등록/해제 대칭 + 주기적 청소 + 제거 대기 큐 + **경과 시간 주입**.

### 좋은 점
- **팝인이 원천적으로 없다.** 아무도 사라지거나 생기지 않는다
- **밀집에서 유일하게 효과가 있다.** 다 가까이 있어도 등급을 나눠 깎을 수 있다
- 방법4와 축이 직교하므로 **같이 쓸 수 있다**
- 업계 주류 방향과 일치한다 (→ [06_References](06_References.md))

### 나쁜 점
- **메모리가 1바이트도 안 준다.** 아무도 지우지 않으므로
- **규모에 약하다.** 맵이 10배가 되면 2Hz 버킷도 10배가 되고 오브젝트도 10배 그대로다.
  방법1보다 훨씬 완만할 뿐 **여전히 N에 비례한다**
- 멀리 있는 개체의 반응이 둔해진다

### 범위를 좁게 자를 것
**틱 버킷 3개 + 위상 오프셋까지만.** 중요도 점수·타입별 예산(Significance Manager 급)은 손대지 말고
"다음 단계"로 남긴다. 착수 판단 근거는 방법4 실측에서 나오는 **35m 내 몬스터 수 분포**.

## 검토 후 기각 — 인접 섹터도 함께 켜기

방법2를 보면 가장 먼저 떠오르는 개선이지만 **구현하지 않고 각주로만 남긴다.**

1. **데이터가 썩는다** — 섹터를 옮기거나 추가할 때마다 이웃 목록을 손봐야 하고, 안 고치면 조용히 틀린다
2. **단위 크기가 안 맞는다** — 화면 25m인데 섹터 100m. 인접까지 켜면 낭비가 2~3배

구현해서 재는 비용 대비 결론이 뻔하다. 다만 **"검토했고 왜 버렸는지"는 반드시 남긴다** —
없으면 "생각 못 했나"로 읽히고, 있으면 "따져보고 버렸구나"가 된다.
