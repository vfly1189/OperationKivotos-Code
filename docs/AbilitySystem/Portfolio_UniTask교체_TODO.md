# 포트폴리오 UniTask → AbilitySystem 교체 작업 문서

> 2026-07-11 검토 결과. 내일 처리용 TODO + 근거 정리.
> 대상: `이형규-포트폴리오.pdf`의 블루 아카이브 프로젝트 中 UniTask 섹션(11~13p, 3장)을 AbilitySystem으로 교체.
> 참고: [AbilitySystem_Portfolio.md](AbilitySystem_Portfolio.md)

---

## 결론

**교체가 맞다.** 게임 클라이언트(게임플레이) 직무 기준:

- UniTask 섹션은 본질이 "라이브러리 도입기". PlayerLoop·레이스 컨디션 분석은 좋지만 "플러그인 선택 근거" 이상으로 확장이 안 되고, 코루틴 vs UniTask 비교표는 널리 알려진 내용이라 차별화 약함.
- AbilitySystem은 "시스템을 설계하고 소유한" 스토리. 3진영(플레이어/몹/보스) 발동 경로 통합 + 데이터 주도 + 조합 기반 확장 = 게임플레이 클라 실무와 정확히 겹침.
- 이터널 리턴 "FSM 기반 스킬 시스템"(18p) → 블아 "데이터 주도 AbilitySystem"으로 **프로젝트 간 성장 서사**가 생김. FSM→BT 개선 스토리와 같은 결.
- **UniTask를 완전히 버리지 말 것**: AbilityRunner/Effect가 전부 UniTask + CancellationToken 위에서 동작하므로 "비동기 실행 부품의 생명주기를 destroyCancellationToken으로 관리" 한 줄로 흡수. 5p Tech 표기의 UniTask도 유지.

## ① 슬라이드 만들기 전 코드 정리 (필수 2건)

"요청 → 유효검사 → 발동" 중 **발동(조립) 파트는 코드가 잘 받쳐주지만, "유효검사" 상자가 반쯤 비어 있음.**

### 1. `Cost` 검사 구현 or 삭제
- `AbilityData.cs:31`에 `public int Cost = 0;` 선언만 있고 **어디서도 검사·소모하지 않음** (grep 확인 완료).
- 현재 유효검사 = `AbilityRunner.IsOnCooldown` 하나뿐.
- 슬라이드에 "유효검사" 단계를 그렸는데 면접관이 GitHub에서 쿨다운 체크 한 줄만 발견하면 역효과.
- → **코스트 검사를 구현하든가, 슬라이드에서 Cost를 빼든가** 결정.

### 2. `CanCast` 분리 (거절 사유 반환)
- `AbilityRunner.TryCast`(AbilityRunner.cs:19)가 결과를 안 돌려줌 → 요청자가 거절 사유(쿨다운/코스트 부족)를 알 수 없음 → UI 피드백·AI의 대체 스킬 선택 불가.
- GAS의 `CanActivateAbility`처럼 **동기 `CanCast`(검증) + 비동기 `CastAsync`(실행) 분리** 또는 거절 사유 enum 반환.
- 작은 작업 대비 "유효검사" 단계가 코드로 실체화되는 효과가 큼.

### (면접 대비) 쿨다운 정책 답변 준비
- 현재: 쿨다운이 캐스트타임 **시작 전에** 돌기 시작하고, 캐스트 중 취소돼도 쿨다운 소모됨 (`TryCast`에서 `StartCooldown` → CastTime 대기 순서).
- 의도라면 OK. 면접에서 물어볼 수 있으니 답 준비.

## ② 발동(조립) 파트 — 이미 잘 된 것 (슬라이드 소재)

- `EffectData(SO) ↔ IEffect(런타임)` 분리. 상태 없으면 `CreateRuntime() => this`(GC 0), 상태 있으면 `new` — 프리팹↔인스턴스 비유로 설명.
- `RepeatEffect` 같은 컨테이너 부품 + Flow 계열(Delay/SelectRandom/Branch) — "투사체·이펙트·패턴을 일반화해 조립" 주장과 코드 일치.
- 투사체 스냅샷 배달(시전자 사망·풀 반환 후에도 안전, 데미지는 명중 시점) — 면접에서 잘 먹히는 디테일.

## ③ 얹으면 좋은 것 / 같은 결의 패턴 (우선순위 순)

1. **입력 버퍼 (Command 패턴 + 타임스탬프 큐) — 강력 추천**
   - 공격 모션 중 눌린 Q를 버리지 않고 N ms 보관 → 모션 종료 시점에 꺼내서 **다시 유효검사로 진입**.
   - "요청→유효검사→발동" 파이프라인의 '요청' 앞단에 자연스럽게 붙음. 액션 게임 조작감 이해 시그널.
   - 애니메이션 캔슬 윈도우(특정 프레임 구간에서만 버퍼 소비)까지 하면 슬롯 키+애니 이벤트 설계와 연결됨.

2. **GameplayTag-lite (차단 태그)**
   - 어빌리티가 태그를 부여/요구/차단 — "기절 중엔 전부 차단", "캐스팅 중엔 평타 차단".
   - `[Flags] enum` 수준 라이트 구현이면 충분.
   - 유효검사를 쿨다운+코스트+태그로 확장 → **"검증도 실행처럼 조합 가능"이라는 대칭 구조**. 발표 포인트로 좋음.

3. **타게팅 부품화 (`ITargetProvider`)**
   - 현재 `AbilityContext.TargetPoint`를 캐스터가 직접 채움.
   - '어디에'(자기/대상/지점/부채꼴)를 데이터 블록으로 빼면 발동의 마지막 하드코딩이 사라지고 조립 스토리 완결.

※ 1·2번은 미구현이어도 "한계와 개선" 슬라이드에 개선 방향으로 배치하면 로드맵 인식으로 점수.

## ④ 발표 전략 주의사항

- **"GAS에서 착안" → 반드시 "무엇을 의도적으로 뺐는가" 질문 옴.**
  - 준비 답: "네트워크 예측/리플리케이션, AttributeSet, GameplayCue는 1인 싱글플레이 범위 밖이라 제외. Ability+Effect 조합 축만 서브셋으로 채택."
  - 이 내용을 한 장으로 — QuadTree 섹션의 "현재 구현의 한계와 개선 방향"(30p)과 같은 포맷이라 포트폴리오 톤과 일치.
- **"외부인/디자이너가 편집 가능" 표현 조심.** 1인 프로젝트라 협업 검증이 없음 → "코드 수정·재컴파일 없이 asset 조합만으로 신규 스킬 제작"처럼 사실 기반으로.

## ⑤ 슬라이드 구성안 (기존 포트폴리오 포맷 유지)

1. **문제상황** — 3갈래 하드코딩 Before 다이어그램 ([AbilitySystem_Portfolio.md](AbilitySystem_Portfolio.md) §1 내용 활용)
2. **문제해결 1** — "요청→유효검사→발동" 파이프라인 그림 (Runner/Data/Effect)
3. **문제해결 2** — 스킬 = Effect 조합. "라이플 5연사" asset 인스펙터 스크린샷
4. **왜 상속이 아니라 조합인가** — 비교표 (Portfolio.md §7)
5. **한계와 개선** — GAS 서브셋 선택 근거 + 입력 버퍼·태그 로드맵

분량: 기존 3장 → 4~5장. 목차 페이지(4p)와 프로젝트 목차(5p)의 UniTask 항목도 같이 교체할 것.
