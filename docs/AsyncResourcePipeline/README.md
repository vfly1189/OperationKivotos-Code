# 동기 일괄 로딩 → Addressable 비동기 리소스 파이프라인

> **한 줄 요약** — 이전 프로젝트의 **동기식 일괄 로딩**이 야기하던 메인스레드 프리즈·메모리 상주·확장성 한계를, **Addressable + UniTask 기반 비동기 리소스 파이프라인**으로 재설계하고, 그 파이프라인의 **메모리 수명 관리**와 **스폰 비용**을 프로파일러 측정으로 검증·최적화했다.

| 축 | 이전(동기 일괄) | 현재(비동기 파이프라인) |
|---|---|---|
| 로딩 | 시작 시 전량 로드 → 메인스레드 블록 | 필요분만 비동기 로드, 메인스레드 비차단 |
| 메모리 | 전량 상주, 씬별 해제 없음 | global/scene 버킷 분리 → 씬 전환 시 씬 리소스만 해제 |
| 생성 | 매번 신규 Instantiate | 오브젝트 풀 재사용 |
| 피드백 | 없음(정지 화면) | 프리로드 진행률 |

> **측정 원칙**: "동기→비동기"는 재현 불가한 이전 프로젝트와의 비교이므로 **설계 동기(정성)** 로 다루고, 성능 근거는 **현재 파이프라인 내부의 최적화(정량, 프로파일러)** 로 제시한다.

---

## 1. 배경 — 동기식 일괄 로딩의 한계

> 〔작성 메모: 이전 프로젝트에서 겪은 구체 사례/수치를 여기에 보강〕

- **메인스레드 프리즈**: 씬 진입 시 모든 리소스를 동기 로드 → 로딩 중 프레임 정지, 진행률 표시 불가
- **메모리 상주**: 당장 필요 없는 에셋까지 전부 메모리에 올리고, 씬이 바뀌어도 해제 시점이 불명확
- **확장성 부재**: 콘텐츠가 늘수록 초기 로딩 시간이 선형으로 증가
- **강한 결합**: 로딩 완료를 콜백/폴링으로 기다리며 코드가 절차적으로 얽힘

→ 이 한계를 개선하기 위해 **비동기 스트리밍 + 명시적 메모리 수명 관리**를 목표로 파이프라인을 재설계.

---

## 2. 파이프라인 설계

```text
[데이터]  Excel → JSON / ScriptableObject (무엇을 로드/스폰할지)
   │
   ▼
[로드]    Addressable 비동기 로드 (UniTask)          ← 메인스레드 비차단
   │
   ▼
[캐시/수명] global 핸들(영구) · scene 핸들(씬 단위)   ← refcount 기반 해제
   │
   ▼
[인스턴스화] 오브젝트 풀 (Poolable → Pool.Pop/Push)   ← 신규 생성 비용 제거
   │
   ▼
[소비]    스포너 / 팩토리 (MonsterFactory)
```

**핵심 컴포넌트: `ResourceManager`**
- **global vs scene 핸들 버킷 분리**: 플레이어·공용 UI 등은 global(게임 종료까지 유지), 맵·몬스터 등은 scene(씬 이동 시 일괄 Release)
- **핸들/아틀라스 캐시**: 중복 로드 방지, SpriteAtlas 조각 캐싱
- **프리로드**: 라벨 단위 선로딩 + 진행률 콜백(로딩 화면)
- **풀 위임**: `Instantiate` 시 Poolable이면 풀에서 재사용

## 3. 최적화 성과 (프로파일러 측정)

### 3-1. 메모리 수명 — global/scene 버킷 + 누수 0 검증

- 씬(GameScene ↔ Dungeon)을 반복 왕복해도 **무거운 Addressable 에셋(텍스처/메시)이 누적되지 않음**을 Memory Profiler로 검증 → scene 핸들 Release 정상 동작 확인
- 이 과정에서 발견한 **런타임 UI 누수(몬스터 HP바)** 를 추적·해결
  - 📄 상세: **[케이스 1 — 씬 반복 전환 시 UI 메모리 누수 추적](../TroubleShooting/MemoryLeak-MonsterHPBar)**
  - 결과: 왕복당 UI 오브젝트 증가 **`GameObject +291 → +3`**, uGUI 누적 완전 소멸

### 3-2. 스폰 비용 — 풀링 미적용 버그 발견·수정

- **스트레스 테스트**(전체 섹터 동시 활성 = 대량 스폰)로 스폰 프레임 스파이크를 증폭시켜 원인을 드러냄
- CPU Profiler 드릴다운 → `UpdateScene`의 **`Instantiate` 363회 / 267ms**가 스파이크의 대부분임을 확인
- 근본 원인: `MonsterFactory`의 async 생성 경로가 **풀을 우회하고 `Object.Instantiate`를 직접 호출** → 디스폰은 풀에 Push하지만 스폰은 Pop하지 않아 **풀이 재사용되지 않음**
- 수정: 생성 경로를 **`Managers.Resource.Instantiate`(풀 경유)** 로 통일

| 시나리오 | 프레임 | 생성 방식 |
|---|---|---|
| 스트레스(전체) - 콜드 | 356ms | `Instantiate.Copy` 363회 |
| 스트레스(전체) - 웜(수정 전) | 323ms | 여전히 363회 신규 생성(풀 미작동) |
| 스트레스(전체) - 웜(수정 후) | **194ms** | `Instantiate.Copy` 제거 → 풀 재사용(`GameObject.Activate`) |

> **설계 판단**: 최종 게임플레이는 **단일 섹터만 활성**하는 구조이므로, 전체 동시 스폰(363개)은 실제로 발생하지 않는다. 전체 활성은 **버그를 증폭시키는 스트레스 테스트**로만 사용했고, 실 시나리오(단일 섹터 진입)의 스폰 비용은 작다. 따라서 **프레임 예산 스트리밍은 불필요하다고 판단**하고, 근본 원인(풀 미적용)만 수정했다. 〔단일 섹터 진입 프레임 수치 보강 예정〕

## 4. UniTask 채택 근거 (Task·코루틴 대비)

- **코루틴 불가**: `ResourceManager`/`DataManager`/`SaveManager`/`SectorManager`가 **비-MonoBehaviour POCO** → 코루틴은 호스트 없이는 실행 불가. UniTask는 POCO에서 그대로 async 실행
- **제로 얼로케이션**: struct 기반 awaitable → `Task`의 상태머신 박싱/GC 압박 회피
- **PlayerLoop 통합**: `PlayerLoopTiming`으로 실행 타이밍을 프레임 단위 제어(Task 불가)
- **Unity 수명 통합**: `GetCancellationTokenOnDestroy` 등으로 파괴 시 자동 취소, Addressable 핸들을 `.ToUniTask()`로 직접 await

---

## 5. 회고

- **측정 없는 최적화는 주장에 불과하다** — 변수를 통제한 시나리오 → 프로파일러 근본원인 특정 → 수정 → 재측정의 루프를 표준으로 삼았다.
- **스트레스 테스트로 숨은 버그를 증폭**시켜, 실제로는 풀링이 동작하지 않던 문제를 드러냈다.
- **누수(수정)와 정상 풀 성장(유지)을 구분**하고, 단일 섹터 설계에선 프레임 예산이 **불필요함도 근거로 판단**했다 — 문제를 만드는 것만큼 **안 만드는 판단**도 최적화다.
